Cloud Bigtable Today

The 2006 engine, run by Google: nodes that hold no data, built-in replication and twenty years of new features

DECK 11 · Bigtable today

How the 2006 design became a managed service

How instances, clusters, nodes and replication fit together

Which modern feature solves which problem

This deck jumps twenty years. The system in the 2006 paper never stopped running inside Google, and since 2015 anyone can rent it as Cloud Bigtable (Google's docs now mostly say just "Bigtable"). First we see what stayed the same, the engine: sorted rows, tablets, a log plus SSTables on a shared file system, single-row atomicity. Then what changed around it: Google runs it, frontends route requests, data rests in Colossus, and replication between clusters is built in. Next come the knobs you turn today: instances, clusters, nodes, storage type, autoscaling and app profiles, and what each does to latency, consistency and cost. Last, a tour of modern features (SQL, change streams, Data Boost, materialized views, aggregate counters), grouped by the problem they solve. "2006" or "the paper" means the system the paper describes; "Cloud Bigtable" or "today" means the service as documented in 2026. Cloud figures change, so check the current docs before designing around one.

2

Bigtable ran in production inside Google from April 2005. The paper appeared at OSDI in November 2006; as of August 2006 Google ran 388 non-test Bigtable clusters. The paper's conclusion listed three projects in progress, and all three shipped (the blue dots). Bigtable as a service: shared internal service clusters by 2009, then Cloud Bigtable for everyone, beta in May 2015 (reached through the HBase API) and generally available (GA) in 2016. Replicated Bigtables: built-in replication between clusters, GA within a region in 2018 and across regions in 2019, today up to 8 regions. Secondary indexes: continuous materialized views, GA in April 2026, usable as asynchronous secondary indexes. Along the way GFS gave way to Colossus, autoscaling arrived (GA December 2021), and in 2025 GoogleSQL for Bigtable became GA, a reversal for a system its own team described in 2008 as not supporting SQL. A common misconception is that Spanner replaced Bigtable. It did not: transactional work moved to Spanner, while Bigtable kept the high-volume key-and-range jobs and kept growing.

3

Put the paper's deployment next to Cloud Bigtable and four differences stand out: call them the four Rs. Run: in 2006 a product group typically looked after its own cluster; today Google operates every machine and you choose settings. Route: in 2006 the client library found each tablet itself (Chubby file, root tablet, METADATA, then a cache); today a frontend server pool forwards every request to the node serving its tablet. Rest: data never lived on the serving machines in either era. SSTables and one commit log per server sat in GFS; today SSTables and a shared log sit in Colossus. Replicate: in 2006 a cluster was normally one copy, and only some tables (Personalized Search) were copied elsewhere; today every table is copied to every cluster of the instance. The engine did not change. The 2006 tuning knobs (locality groups, compression, Bloom filters, block size) are now Google's job; you keep the row key, families, GC rules and capacity.

Recording a card payment

4

Google describes today's architecture in four layers. The client library sends every request to a frontend server pool, which forwards it to the node serving the tablet whose key range holds the row. "Node" is the modern word for the paper's tablet server; each tablet is served by exactly one node at a time. Under everything sits Colossus, GFS's successor, holding SSTable files and a shared log of every acknowledged write. A primary process in each zone decides which node serves which tablet and splits and merges tablets, jobs the paper gave to the master and tablet servers. Follow the write: MutateRow for acct#8812#… reaches a frontend, which forwards it to Node 2 (tablet T4). The write is stored in the shared log, so the "ok" means it survives a node crash; the node also keeps it in memory (the LSM pattern of deck 08). The exact order of these steps is not published. A read takes the same route, merging memory with SSTables and reading blocks from Colossus on a cache miss. How frontends find tablets is also unpublished.

5

The Cloud docs are blunt: data is never stored in Bigtable nodes themselves. A node holds pointers to its tablets in Colossus, plus memory and caches. The picture shows Node 4 joining. Node 3 used to serve T7 and T8; the primary process hands those two pointers to Node 4 and nothing is copied, like a helpdesk lead handing a new agent two queues while the tickets stay in the shared system. A shared-nothing database such as Cassandra keeps data on local disks and must first stream a share to a new server. Three benefits follow: fast rebalancing (no data is copied), fast recovery (only metadata moves to a replacement node), and no data lost when a node fails (every acknowledged write is already in the shared log). The 2006 design worked the same way with GFS. The costs: a cache miss is a network read; new nodes take up to 20 minutes under load to help; a node carries at most 5 TB of SSD data; idle nodes are billed; no split can divide one hot row.

6

Resources nest four levels deep: project, instance, cluster, node (remember P-I-C-Nic, a picnic packed from the outside in). The project owns billing, permissions and quotas; the instance owns the tables and the storage type. A cluster is the instance's presence in one zone and holds a full copy of every table on Colossus in that zone. As of 2026: one cluster per zone, clusters in up to 8 regions, and each cluster has its own node count. Nodes are compute and hold no data. Size each cluster by the larger of two needs: CPU and storage (at most 5 TB per SSD node, 16 TB per HDD node). SSD or HDD is chosen once, when the instance is created; switching means a new instance. Google does not spell out why HDD reads suffer, but the engine explains it: writes go to a log and memory and are later written sequentially, while each uncached point read needs a disk seek of about 10 ms. The bars are Google's 2026 per-node estimates for 1 KB rows, a starting point for load tests.

7

Autoscaling (GA December 2021) changes each cluster's node count for you, like a thermostat. You set a CPU utilisation target between 10% and 80%, a storage target (default 50%, which means 2.5 TB per SSD node), a minimum node count and a maximum of at most ten times the minimum. Each dimension recommends a node count and Bigtable uses the higher one. Above the CPU target it adds nodes immediately; it removes them only when CPU is well below the target, and more slowly, so a short lull does not leave you short when the next rush comes. In a replicated instance each cluster autoscales on its own. The chart is an illustrative day, not real data: the blue line jumps up with demand, steps down late and never drops below the minimum of 6. In Google's day-and-night experiment (2022 blog) the cluster averaged 15.84 nodes against a 27-node peak, about 41% cheaper than sizing for the peak. Limits: new nodes need up to about 20 minutes under load to help, and no number of nodes fixes one hot row.

WATCH OUT

Clusters don't add write capacity

Every cluster applies every write.

8

Every cluster of a replicated instance holds a full copy and accepts reads and writes. A cluster acknowledges a write as soon as it is durable in its own zone, then ships it to the others in the background. Nobody waits for distance; a synchronous round trip from California to the Netherlands would add about 150 ms per write. Follow the lanes. (1) The US checkout sets a payment to settled; cluster A says ok within milliseconds. (2) A dashboard in Europe reads cluster B and still sees pending: a stale read, which eventual consistency allows. (3) The cell, with its original timestamp, is copied to B, typically within seconds or minutes. (4) The next read in B sees settled. If writes stop, all clusters converge. Even the writer can miss its own write if its next request lands on another cluster, like the laptop in the example. Inside one cluster nothing changed since the paper: a read after an acknowledged write sees it. Every cluster applies every write, so extra clusters add reads, locality and availability, not write capacity.

A payments platform uses both

9

An app profile is a named set of instructions, stored in the instance, telling Bigtable how to handle one application's requests. The client names it when it opens a table; Google recommends one profile per workload. Single-cluster routing sends every request to one named cluster. Its readers get strong consistency, so an app always reads its own acknowledged writes; single-row transactions (check-and-mutate, read-modify-write) can be enabled; failover is manual: someone edits the profile. Multi-cluster routing sends each request to the nearest available cluster and fails over automatically. Consistency is eventual, so your next read may land on a cluster that has not received your write yet, and single-row transactions are not allowed. Variants: a cluster group limits routing to some clusters, and row-affinity routing picks the cluster from the row key, so read-your-writes happens more often but is not guaranteed. Watch the default profile: it is set when the instance is created and does not change when you add clusters. The SLA rewards multi-cluster routing: 99.9% single-cluster, up to 99.999% with clusters in three or more regions.

ONE CLUSTER IS FINE

One node owns the row and applies increments in turn.

10

Why does Bigtable block read-modify-write increments under multi-cluster routing? An increment reads the current value in the cluster that receives it and writes a new total. Two clusters can each read 5 and each write 6. After replication a read returns only the newest cell, which holds 6 either way, so one increment is lost. Inside one cluster this cannot happen: one node owns the row and runs the operations one after another. That is why check-and-mutate and read-modify-write need a single-cluster profile with transactions enabled. For counters updated everywhere, use an aggregate column family (GA August 2024). Its cells are CRDTs, conflict-free replicated data types: you send an input (AddToCell +1), and the merge (Sum, Min, Max or HyperLogLog) gives the same answer in any order. Both clusters end at 7. Truncate the timestamp to the hour and inputs merge into one cell per hour. Caveat: AddToCell is not idempotent, so a retried +1 counts twice; keep raw events if exact totals matter.

The 2006 engine still runs underneath; around it Google added features the source sorts into seven groups: "see it, guard it, feed it, ask it, count it, run it, port it". See: Key Visualizer (a heatmap of load by key range) and the hot-tablets list. Guard: backups, deletion protection and undelete, IAM and authorized views. Feed: change streams, Data Boost, BigQuery and pipeline connectors. Ask: GoogleSQL for Bigtable (GA April 2025, read-only), logical views, continuous materialized views (GA April 2026). Count: aggregate column families. Run: request priorities, tiered storage and the in-memory tier (both Preview as of October 2026; the in-memory tier needs the Enterprise Plus edition). Port: the HBase API since the 2015 launch, and the Cassandra-Bigtable proxy. Green pills mark generally available features with their GA year; grey marks Preview, which may still change and is usually outside the SLA. Stages move, so check the release notes. 12

Change data capture turns every change into an event other systems consume. Polling is wasteful and blind to deletes; writing to Bigtable and also publishing an event can disagree when one of the two fails. With a change stream on a table (GA July 2023), Bigtable records every committed change: mutations, increments, row-range drops, and deletions made by garbage collection. Each record holds the new value only, plus the commit timestamp and the cluster where the write happened. The stream is split into partitions, one per tablet, which split and merge as tablets do. Order is guaranteed per row key per cluster; there is no order across rows. Records are kept 1 to 7 days. A Dataflow (Apache Beam) pipeline keeps one reader per partition; Google ships templates for BigQuery and Pub/Sub. A per-partition low watermark tells the pipeline when a time window is complete. Google's cost estimate: about 10% extra CPU with a stream enabled, 20 to 30% while it is read, and storage of about 1.5 times the data written per day of retention.

Bigtable serves many small reads and writes in milliseconds; analytics wants a few huge jobs that read everything. Run those through the serving nodes and users feel it. Data Boost (GA February 2025) runs read jobs on serverless compute that Google provisions on demand, separate from your nodes. You opt in per workload with a Data Boost app profile (single-cluster routing only). The scan that pushed node CPU to 95% now leaves it at 45%. It works because nodes never held the data, only pointers to tablets on Colossus, so a second pool of machines can read the same files; there is still one copy. Google does not document the internal read path, so the dashed arrow from Colossus to Data Boost is an inference. Rules: Data Boost is guaranteed to see data written more than 35 minutes before the request; it is read-only, not for point reads or latency-sensitive work, and not for CMEK tables. It is billed in serverless processing units only while jobs run. Alternatives: a low request priority (free, same nodes) or a separate analytics cluster.

NEXT Deck 12 · Schema design and real workloads

14

Five ideas to keep. First, the engine is the 2006 one; what changed is who runs it (Google), how requests are routed (frontends instead of METADATA lookups), where data rests (Colossus with a shared log) and that replication is built in. Second, nodes are compute that point at tablets on Colossus. Splitting, balancing, scaling and recovery move pointers, which is why a node failure loses no acknowledged write. It is not instant: new nodes need up to about 20 minutes under load, and no node count fixes one hot row. Third, replication is asynchronous and multi-primary; more clusters add reads, locality and availability, never write capacity. Fourth, app profiles pick the trade per workload: single-cluster routing for strong reads and single-row transactions, multi-cluster routing for automatic failover with eventual consistency. Counters updated in every cluster belong in aggregate families. Fifth, start from the problem when picking a feature. Next deck: the decision that still matters most, the row key.
