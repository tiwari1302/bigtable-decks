Distributed Systems Basics

Failure, partitioning, copies, leaders and majorities: the ideas Bigtable is built on

DECK 02 · Foundations

Why machines fail every day, and why silence is ambiguous

How data is split across machines and copied for safety

How a system keeps exactly one leader and agrees by majority

This is deck 02 of "Bigtable, Visually", in the Foundations part of the series. Bigtable is a distributed system: a group of computers that cooperate over a network and try to look like one system to the people using it. Each computer is a node. Nodes cannot see each other. All they have are messages, and messages can be late, lost or never answered. Almost every idea in this deck is a way of coping with that one fact. Ten short concept slides cover six ideas, each with a picture and an everyday example: failures are normal; splitting data by hash or by range; keeping copies; keeping exactly one leader with leases; agreeing by majority; and what a reader may see after a write. The last content slide maps every idea onto Bigtable, so you can recognise them when later decks open up the machine. If you already know sharding, leases and Paxos, skim the pictures and jump to the map slide.

A server that breaks once every three years sounds reliable. Now run a thousand of them. Three years is about 1,095 days, so each machine has roughly a 1-in-1,095 chance of failing on any given day. Across the fleet that is 1,000 ÷ 1,095 ≈ 0.91 failures a day, and the chance that at least one machine fails today is about 60%. The week in the picture is illustrative. Real life is worse, because failures come in bursts. Jeff Dean's 2009 talk lists, for a typical first year of a new Google cluster, about 1,000 machine failures, thousands of hard-drive failures, about 20 rack failures and a power-distribution failure that takes out 500 to 1,000 machines for about 6 hours. These numbers come from that talk, not from the Bigtable paper. The consequence shapes everything else: recovery cannot be a rare manual event. In Bigtable, a dead tablet server's work is reassigned and rebuilt automatically. Real-world example: stadium light bulbs. Each lasts for years, but with thousands of them, replacing a few every week is routine.

3

"Failure" is not one thing. A crash (also called fail-stop) means the process simply stops. A hung or slow machine is still alive but stuck: swapping, overloaded, or paused by a long garbage collection. A network partition cuts the network so that two groups of healthy machines cannot reach each other; it can even be one-way. From the caller's side all three look exactly the same: silence. A node cannot tell dead from slow from unreachable. Its only tool is a timeout: if I hear nothing within T seconds, I assume the worst. Choosing T is a trade-off. Too short, and slow but healthy machines are declared dead, causing needless recovery work. Too long, and real failures take ages to handle. Worse, a node that has been declared dead may still be running and acting on old beliefs. That problem drives the leader and lease slides later. Two more failure kinds raise no error at all: corrupted bytes (caught by checksums) and clock skew (small skew is absorbed by lease safety margins). Real-world example: an unanswered phone call.

4

Partitioning, also called sharding, divides a dataset into pieces, each served by one machine. Every client needs a fast rule: given a key, which machine holds it? Hash partitioning computes server = hash(key) mod N. Keys spread evenly and no lookup table is needed. But neighbours scatter, so a scan of a key range must ask every server, and changing N moves most keys: going from 4 to 5 servers moves about 80% of the data (derived arithmetic). Range partitioning sorts the keys and cuts the sorted list into contiguous slices, with a small table of split points. Neighbours stay together, so a scan touches one or two servers, and a slice that grows can be split in two. Bigtable chose ranges: every table is sorted by row key and cut into tablets, the unit of distribution and load balancing. In the 2006 paper a tablet was about 100 to 200 MB by default; Cloud Bigtable no longer publishes a size and splits on both size and load. Real-world example: lockers assigned by number versus a dictionary split into volumes.

Range partitioning has a price: the hotspot, one server receiving a disproportionate share of the traffic while the others idle. Both rows show the same four sensor readings arriving one second apart. In the top row the row key starts with the time. Every new reading has the newest time, so it sorts after every old key and lands in the last tablet. One server does all the work. Splitting that tablet does not help much: the next writes land at the very end again. The cure is in the key, not the system. In the bottom row the key starts with the sensor id, a high-cardinality field (one with many different values). The same four writes now spread over all four tablets, and one sensor's readings still sit together for range scans. Cloud Bigtable's schema guide (as of 2026) gives the same advice: do not start row keys with a timestamp; lead with a high-cardinality id. Deck 12 covers more fixes. 6

Replication means keeping copies of the same data on several machines. It serves two goals: durability (a lost disk loses no acknowledged write) and availability (the system keeps answering while some machines are down). Copies cost something: every write must reach several machines before it counts. The 2006 Bigtable design makes a deliberate split. It replicates bytes: a tablet's files live in GFS, the Google File System, which by default keeps every chunk on three machines across racks. It replicates coordination state in Chubby, a lock service with five replicas. But it does not replicate serving: each tablet has exactly one tablet server at a time, with no hot standby. When server B dies, the master gives tablet T3 to server C, which rebuilds it from the copies of T3's files and of B's commit log. The tablet is briefly unavailable. One owner per row keeps correctness simple. Cloud Bigtable keeps the split: data lives in Colossus, and nodes store no data, only pointers to tablets. Real-world example: copies of your passport.

IN THE REAL WORLD

7

Some decisions must be made by exactly one node. "Which tablet server owns tablet T3?" is one of them. Suppose the network splits and each side decides the other is dead. Each side now believes it is in charge, so each hands T3 to a different server. Both servers accept writes for account 8812, each appends to its own log, and the account ends up with two different histories. When the network heals there is no correct balance. This is split brain: two parts of a system each believe they are in charge and act independently. The standard answer is a single leader, picked by leader election. The hard part is guaranteeing there is never more than one. A naive rule such as "the lowest-numbered live machine leads" fails, because "live" is a guess based on timeouts, and during a partition each side sees a different set of live machines. In Bigtable the one decider is the master; the next slide shows how a lease keeps it unique. Real-world example: two captains on one ship.

8

A plain lock is not enough. If its holder crashes, the lock is held forever; if the service frees it when the holder goes quiet, the holder may still be alive and acting. A lease is a lock with an expiry time (Gray and Cheriton, 1989). The holder renews it with small periodic messages called heartbeats. Two rules make it safe: the holder stops acting the moment its lease might have expired, and the service waits until the lease has surely expired, plus a safety margin, before granting it again. Timings are illustrative. A holds a 12-second lease. At 4 s the network cuts A off; A keeps leading by its own clock. At 12 s A stops itself. The service waits out a 2-second margin and grants the lease to B at 14 s. For two seconds there is no leader, but never two. In Bigtable, the master holds the master lock in Chubby and kills itself if its Chubby session expires; Chubby's default lease extension is 12 s (Chubby paper, 2006). Real-world example: a hotel key card.

9

A lock service on one machine is a single point of failure, so it is replicated, and its replicas must agree even while some crash or miss messages. Getting machines to agree on one value, and never on two, is called consensus. The trick is the majority quorum: a decision counts once a majority of replicas accepts it. In a group of 5, two groups of 3 hold 6 seats, so at least one replica sits in both. That shared replica remembers the first decision and blocks a conflicting second one. When the network splits, at most one side can hold a majority, so at most one side can decide. The minority stops answering: it chooses consistency over availability. The rule: majority = ⌊N/2⌋ + 1, and the group survives N minus majority failures. Odd sizes are the sweet spot: 4 replicas survive no more failures than 3. Chubby runs five replicas, so it survives two failures; Bigtable borrows consensus from Chubby instead of running it. Real-world example: a committee of five.

10

Paxos is Leslie Lamport's consensus algorithm; the Chubby paper notes that every working consensus protocol its authors had seen had Paxos at its core. A value is chosen once a majority accepts it, and it can never be replaced, because any future majority contains a replica that accepted it. A new leader must first ask a majority what they have accepted, and re-propose any value it finds. With a stable leader that asking step is skipped, so each decision is one round. The picture follows one decision. Client B, a Bigtable master, asks Chubby for the master lock, so the five replicas must record "lock holder = B". Leader R1 numbers the change #7 and sends it to everyone. R4 has crashed and R5 is slow. R1, R2 and R3 log #7: three of five, so it is chosen and nobody waits. R5 learns #7 soon; R4 catches up when it restarts. Paxos never lets two values be chosen, but it needs a reachable majority to make progress. Raft and ZooKeeper's Zab are cousins. Real-world example: a parliament vote.

11

With copies, a read might reach a copy that has not yet heard about the latest write. A consistency model is the promise a system makes about what reads may return. Ana deposits 50 into account 8812, taking the balance from 100 to 150. Right after the write is acknowledged, she and her accountant Ben both check. Strong consistency (formally, linearizability): every later read, by anyone, sees the write. Read-your-writes: you always see your own writes; others may lag. Eventual: copies converge once writes stop, but until then any read, even the writer's, may be old. Red chips are stale reads the model allows. CAP says that during a network partition a replicated system must choose consistency or availability; PACELC adds that otherwise it trades latency against consistency. Bigtable in one cluster is strong per row, because one server owns each tablet (an inference from the paper; Cloud docs state it for single-cluster instances). Cloud Bigtable with several clusters and multi-cluster routing is eventual: copies typically arrive in seconds to minutes. Real-world example: bank balance versus like count.

Here is where each idea from this deck lives inside Bigtable (the 2006 design). 1 Failures are daily: a tablet server that goes silent loses its Chubby lock, the master reassigns its tablets, and the new owner replays the commit log. 2 Range partitioning: every table is cut into tablets, contiguous row ranges. 3 Replication: GFS keeps three copies of every file; Chubby runs five replicas. Serving is not replicated: one server per tablet. 4 Leases: the master holds the master lock and each tablet server holds a lock file in Chubby; both stop when they lose them. 5 Majorities: Paxos runs inside Chubby, and Bigtable trusts Chubby for its few critical facts. 6 Consistency: one owner per tablet makes each single-row read or write strongly consistent within a cluster. 7 The master stays off the data path: clients find tablets through the METADATA table and cache locations, so most never talk to the master. A mnemonic from the source: Failing Parts Require Leaders, Quorums and Careful Masters. Decks 06 and 07 open each part up.

TEST YOURSELF

Q1. 2,000 machines, each failing once in 4 years: failures a day?

Answer: About 1.4.

Q2. Why is a time-first row key risky?

Answer: All new writes hit the last tablet.

Q3. Multi-cluster routing: a refresh misses a payment. Bug?

Answer: Not necessarily: it is eventually consistent.

13

Five things to remember. One: at thousands of machines failures are daily, and crashed, stuck or cut-off servers all look like silence, so systems act on timeouts. Two: Bigtable splits tables by row range into tablets, keeping neighbours together; keys that always increase create hotspots. Three: the 2006 design copies bytes (GFS, three copies) and coordination state (Chubby, five replicas) but not serving: each tablet has exactly one server. Four: a lease makes "exactly one leader" safe, because the holder stops before the service hands the right to anyone else. Five: majority quorums overlap, so five replicas survive two failures and a minority must pause. Quiz answers: 2,000 ÷ (4 × 365) ≈ 1.4 failures a day, so recovery must be automatic. A time-first key sends every new write to the last tablet; lead with an id such as the sensor. Cloud Bigtable's multi-cluster routing is eventually consistent, so the refresh may reach a cluster the payment has not reached yet; single-cluster routing gives read-your-writes.
