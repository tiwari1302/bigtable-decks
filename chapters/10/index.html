Proof at Google

What the 2006 benchmarks measured, how real Google products used Bigtable, and what its builders learned

DECK 10 · Proof in production

What the 2006 benchmarks measured, and why random reads were slow

How Analytics, Earth and Personalized Search shaped their tables

Four lessons the authors learned running it at Google

This deck covers the part of the 2006 Bigtable paper where the design meets reality: Section 7 (performance), Section 8 (real applications) and Section 9 (lessons). First we read the benchmarks the way an engineer should: every number is a bottleneck you can name. One tablet server did about 15,000 scan values per second but only about 1,200 random reads from GFS, and we will see exactly why. Then we add servers and watch scaling fall short of perfect, for reasons that apply to any distributed system. Next we visit the 2006 fleet (388 clusters, about 24,500 tablet servers) and three products whose schemas still teach good habits: Google Analytics, Google Earth and Personalized Search. We finish with four lessons the authors wrote down after more than a year in production. All numbers are from the 2006 paper unless a slide says Cloud Bigtable, 2026.

2

Section 7 of the paper times six simple workloads on clusters of N = 1, 50, 250 and 500 tablet servers. Each tablet server could use 1 GB of memory and held about 1 GB of data, so most data could not sit in a cache. All servers stored their files in one GFS cell of 1,786 machines, each with two 400 GB IDE drives. Another N machines ran clients, so clients were never the bottleneck. Every machine had one gigabit link (about 125 MB/s); round trips took under a millisecond. Values were 1,000 bytes of random text, which does not compress, so the numbers measure the bare read and write machinery. The detail that shapes the scaling results: the machines were shared. Every machine ran a GFS server; some also ran a tablet server, a client, the master, or someone else’s job. Which process ran where on this slide is illustrative; the paper gives only the mix. Work was handed out as 10N key ranges, on demand, so a slow client simply finished fewer ranges.

This chart is the first column of the table inside the paper’s Figure 6: one tablet server and one client, 1,000-byte values per second. Every cell of that table is a rate per server, not a cluster total. Each bar is explained by one mechanism. Scans are fastest (15,385 values/s) because one RPC returns a long run of values. Random reads from an in-memory locality group (10,811/s) never fetch from GFS. Writes, random or sequential, run at about 8,500 to 8,850/s because every write is appended to one commit log in arrival order, batched by group commit; key order does not matter. Sequential reads (4,425/s) reuse each fetched 64 KB block for about 64 reads. Random reads from GFS are slowest (1,212/s): each one fetches a whole block. The source’s memory aid, “Some Managers Write Slow Reports”, lists them fastest to slowest. Cloud Bigtable, 2026, per SSD node with 1 KB rows: up to 17,000 point reads, 14,000 writes, 220 MB/s of scans. Different hardware and units: compare the shape, not the values.

4

Follow one random read. The client asks for one 1,000-byte value. The block index in memory names the SSTable block, so no disk is touched yet. But the keys are random and the server holds about as much data as its whole 1 GB memory budget, so the block is almost never in the block cache. A whole 64 KB block crosses the network from a GFS chunkserver; the server pulls out one value and the other ~63 KB go unused. That is about 65 bytes moved for every byte used: the read amplification of this workload. At 1,212 reads per second that is about 79 MB/s (our arithmetic; the paper says approximately 75 MB/s), enough to saturate the server’s CPUs and nearly fill its 1 Gbps link. The paper names the fixes. Most such applications shrink the block size, typically to 8 KB, which moves eight times fewer bytes per read (the paper did not benchmark it). Or mark the locality group in-memory: no fetch, 10,811 reads per second (that run used 100 MB of data, not 1 GB).

5

Pairs of runs differ in one main thing; the ratio tells you what that thing costs. Random to sequential reads: the only change is key order. Neighbouring keys sit in the same 64 KB block, so one fetch lands in the block cache and serves about 64 reads: 3.7 times faster. Sequential reads to scans: same rows, same blocks, but a scan returns many values per RPC. Every RPC has a fixed cost (packets, waking a thread, parsing, building the reply), so spreading it over many values makes scans 3.5 times faster again. Reads from memory never fetch, yet at 10,811/s they still trail scans, because each one is still a separate RPC. Why are sequential reads only 3.7 times faster when they cut fetches 64-fold? Because once fetches are mostly gone, the per-RPC cost takes over. Remove one bottleneck and the next one sets the pace. Writes are the odd pair: random 8,850/s versus sequential 8,547/s, because the commit log ignores key order. The diagram shows 8 values; a real block holds about 64.

6

Aggregate throughput is the per-server rate times N; perfect scaling would give 500 times the work at 500 servers. The chart shows random reads: measured totals against perfect. They rose from 1,212 to 119,750 values per second at 250 servers and then stalled at 120,500 at 500 servers: doubling the hardware bought less than 1%. A flat line like that means a shared resource is saturated; here, the paper says, the 64 KB block transfers saturated shared 1 Gbps links. The right panel shows scaling efficiency at 500 servers: the per-server rate divided by the one-server rate (our arithmetic from Figure 6). Reads that fetch little scale best (51 to 58%); random reads (20%) and both writes (22 to 23%) scale worst. Why not linear at all? Load imbalance: other jobs on the shared machines, load that shifts as the run goes on, and a master that throttles tablet moves because each move makes a tablet unavailable, typically for under a second. Cloud Bigtable’s docs (2026) say throughput scales linearly with nodes; still test with production-sized data.

7

In August 2006 Google ran 388 non-test Bigtable clusters with about 24,500 tablet servers in all. The chart redraws the paper’s Table 1 (tablet servers per cluster). Two clusters in three had fewer than 20 tablet servers, and the paper says many clusters were development clusters that sat idle for long stretches. Yet most machines lived in the 62 clusters with 100 or more servers. Even if every smaller cluster were full, they could hold only about 9,200 servers, under 40% of the fleet; the bars on the right show that contrast (our arithmetic). The paper also singles out 14 busy clusters with 8,069 tablet servers. Together they handled more than 1.2 million requests per second, with about 741 MB/s of RPC traffic in and 16 GB/s out, so in bytes the work was mostly reads. That is only about 150 requests per second per server, far below the benchmark peaks. The paper does not explain the gap; likely reasons: one request can be a large scan, load is uneven, and clusters are sized for peaks and for data.

8

Google Analytics reports traffic to website owners. A small JavaScript snippet on each page records every visit. In 2006 the raw click table (about 200 TB) held one row per end-user session, keyed by the website name plus the session’s creation time; the separator and format on the slide are ours. Bigtable sorts rows by key, so every session of one site sits in one contiguous run, oldest first. A report for one site over a day or week is one range scan, with no index. Time-first keys would scatter each site’s sessions and send every new session to the last tablet, a hotspot. Periodic MapReduce jobs read recent sessions and write predefined per-site summaries into a summary table of about 20 TB; the paper does not detail how reports are served. It says GFS throughput limited the whole system. Compression helped: the tables shrink to 14% and 29% of their size. Pattern: raw events keyed for the common scan, plus precomputed rollups. Cloud Bigtable, 2026: Dataflow or BigQuery, Data Boost, aggregate families or continuous materialized views fill these roles.

9

Google Earth and Maps let people pan and zoom satellite imagery. In 2006 one table preprocessed imagery and a different set of tables served clients, tuned in opposite ways. The preprocessing table (about 70 TB) has one row per geographic segment, named so that neighbouring segments sort near each other. A family records which raw images each segment is built from, with essentially one column per image. A segment uses only a few images, so the family is very sparse, and in Bigtable empty cells cost nothing. Images arrive compressed, so Bigtable compression is off. During some MapReduce jobs it processed more than 1 MB/s per tablet server. The serving index is small, about 500 GB, but must answer tens of thousands of queries per second per datacenter with low latency. So it is spread over hundreds of tablet servers and keeps in-memory column families (33% of the table in memory). Storage is not the constraint; request rate is. Cloud Bigtable, 2026: no in-memory flag per group; isolate batch work with a separate cluster (app profiles) or Data Boost.

10

Personalized Search was an opt-in service that recorded a user’s queries and clicks across web search, images, news and more. The schema: one row per user, keyed by user id; one column family per type of action (for example, one for all web queries); and each cell’s timestamp is the time the action happened, so the timestamps form the user’s timeline. Names and values on the slide are made up. A history page reads one row, filtered by family and time. A MapReduce builds a profile per user that personalises live results. Other Google teams added their own per-user columns, which is why the table had 93 column families in 11 locality groups (Table 2). Column families are the unit of access control and accounting, and the Bigtable team added a simple per-client storage quota for isolation. The table was replicated to several clusters, first by client code, later by replication built into the servers; copies were eventually consistent. Cloud Bigtable, 2026: keep rows under about 100 MB (hard limit 256 MB), so cap unbounded histories with GC rules.

11

Many protocols assume fail-stop: a machine either works correctly or halts. Section 9’s first lesson: a large system meets far more. The authors list what they saw in production: memory and network corruption, large clock skew, hung machines, extended and asymmetric network partitions, bugs in other systems such as Chubby, overflow of GFS quotas, and planned and unplanned hardware maintenance. The example is ours. A payment of 125.00 leaves a client; one bit flips in transit and the character 5 (0011 0101) becomes 4 (0011 0100). The tablet server receives a well-formed mutation, logs it and replies ok. No crash, no error. Fix 1 is to check data at boundaries: the paper added checksums to the RPC mechanism, so the receiver detects damaged bytes. (What happens after a mismatch, such as a resend, is our assumption.) Fix 2 is to stop assuming what another component can return: Bigtable had assumed a Chubby operation could fail in only a fixed set of ways. Treat an unexpected answer as unknown, never as fine.

12

Lesson 2: wait until you know how a feature will be used. The team planned general transactions but, with no immediate use, skipped them. Real use showed most applications needed only single-row transactions; the main request for cross-row updates was maintaining secondary indexes. Google later met that need on top of or beside Bigtable: Percolator (2010), Megastore (2011), Spanner (2012), and in Cloud Bigtable continuous materialized views as asynchronous indexes (GA April 2026). Lesson 3: monitor the system and its clients. Sampled RPC tracing records each step of a small fraction of requests with timings; it found lock contention on tablet data structures, slow GFS writes while committing mutations, and stuck METADATA accesses. Every cluster also registers in Chubby, so operators can see the whole fleet. The trace bars here are illustrative. Lesson 4, the paper’s most important: simple designs win. Bigtable was about 100,000 lines of non-test code. The first membership protocol was simple but fragile; fixes made it complex and fast but hard to debug, because it leaned on rarely used Chubby features. A simpler design replaced it.

TEST YOURSELF

Q1. Why do writes ignore key order?

Answer: All go to one log, in arrival order.

Q2. Why did random reads stall past 250 servers?

Answer: Shared links were full; move fewer bytes.

Q3. Why does a 500 GB index need hundreds of servers?

Answer: For request rate, not storage.

13

Five things to keep from this deck. First, read benchmark tables carefully: the paper’s Figure 6 table gives rates per tablet server, and every number is a bottleneck you can name. Second, random reads were slow because each 1,000-byte value cost a 64 KB block fetch from GFS; smaller blocks (typically 8 KB) or in-memory locality groups were the fixes. Third, adding servers helped a lot (about 100 to 300 times for 500 times the servers) but far from perfectly, because of shared machines, throttled rebalancing and saturated shared links. Fourth, the production schemas all follow their dominant query: Analytics keys by site then time, Earth keeps batch and serving tables apart, Personalized Search keeps one row per user. Fifth, the lessons: expect failures beyond clean crashes, build features once real use shows the need, monitor the system and its clients, and prefer simple designs.
