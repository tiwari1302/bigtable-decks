Making It Fast

The tricks that let Bigtable skip disk trips, shrink files and recover quickly

DECK 09 · Making it fast

How locality groups, compression and caches cut the bytes a read touches

How a Bloom filter says “definitely not here” without opening a file

How one shared log and sealed files keep writes, moves and recovery fast

This deck covers Section 6 of the 2006 Bigtable paper: the refinements that turn the basic design from the earlier decks into a fast system. The basic design works, but it has costs. A read may have to look inside every SSTable of a tablet, and each look can cost a trip to disk, about 10 ms per seek in Jeff Dean’s widely quoted 2009 latency table. Hundreds of tablets share one server and its writes, and crashes, moves and splits all need handling. We follow the paper’s seven refinements in order: locality groups, compression, caching, Bloom filters, the commit-log design, faster tablet recovery, and exploiting immutability. The source’s mnemonic for them is “Lucy Can Catch Big Crabs Really Instantly”. Each slide shows the mechanism, a real-world example and the key numbers. Numbers are from the 2006 paper unless marked otherwise. In Cloud Bigtable (2026) most of these knobs are managed by the service, but the habits behind them, good row keys and sensible column families, still pay off.

A locality group is a set of column families that the client asks Bigtable to store together, apart from other families. The rule (§6): each locality group gets its own SSTables in every tablet. Take Webtable, where each row is a web page. A job that counts pages per language needs a few dozen bytes per row. With every family in one group (A), each tiny language: cell sits in the same 64 KB block as tens of kilobytes of HTML, so the job reads every block. With made-up but plausible sizes, it uses one byte in every 1,800 it pulls from GFS. With language: and checksum: in their own group (B), the job reads one small SSTable stack and never opens the page files. The data model is unchanged: a mutation is still atomic across families, with one commit log. The cost: reads that span groups merge more files, so group families by who reads them together. Personalized Search had 93 families in 11 groups (2006, Table 2). Cloud Bigtable (2026) does not let you specify locality groups.

Each locality group is also the unit of tuning. The paper names four settings per group; a handy mnemonic is “My Cat Bites Books”: in-Memory, Compression, Block size, Bloom filter. An in-memory group has its SSTables loaded into the tablet server’s RAM, lazily: nothing is copied up front. The SSTables stay in GFS and writes still go to the commit log, so a crash loses only the copy; the next server recovers the tablet as usual and loads the group again. Bigtable uses this itself: the METADATA table’s location family is in-memory, so tablet lookups need no GFS reads. In the 2006 benchmark one server did 10,811 random reads per second from an in-memory group against 1,212 from GFS, about 9 times faster (with data per server cut from 1 GB to 100 MB so it fit). In production (Table 2, 2006), Google Earth’s serving index kept 33% in memory and Google Base 15%; the biggest tables kept none. Cloud Bigtable (2026) has no per-group flag; an in-memory tier (Enterprise Plus, Preview) caches rows by usage instead.

4

In the 2006 paper the client chooses, per locality group, whether SSTables are compressed and with which format. The format is applied to each block separately, so every block is a self-contained unit. Follow one read: the in-memory block index says the cell is in b3, with no disk access. Only b3 crosses the network, and it is smaller than 64 KB because it is compressed. The server expands it; at the paper’s decode speeds of 400–1000 MB/s that takes about 0.06–0.16 ms (derived), tiny next to a 10 ms disk seek. If the whole file were one compressed stream, the server could not start in the middle; it would decompress from the beginning. The price is some space, because a block cannot point at repeats in other blocks; the paper accepts that on purpose. Compression is switched off where data is already compressed, as for Google Earth’s raw imagery. Cloud Bigtable (2026): compression is automatic and not configurable; compress values over 1 MiB yourself.

5

Many clients picked a custom two-pass scheme. Pass 1 (Bentley and McIlroy, 1999) finds long common strings across a large window and replaces each with a short “copy this many bytes from there” reference. Pass 2 is a fast compressor that looks for short repeats within a 16 KB window: HTML tags, common words. Both are fast: encode at 100–200 MB/s and decode at 400–1000 MB/s on 2006 machines. In one experiment Webtable stored many pages, one version each, in a compressed locality group and got 10 to 1; gzip typically gets 3 or 4 to 1 on HTML. The row key explains the gap: reversed-URL keys sort one host’s pages side by side, and those pages share headers, navigation and footers. Pass 1 finds exactly those long repeats, which gzip’s 32 KB window misses. Storing several versions compresses even better, but the 10 to 1 used one. Lesson: row-key design is compression design. Cloud Bigtable’s docs (2026) agree: compression works best when identical values sit near each other.

6

A cache keeps copies of data whose real home is slower. A 2006 tablet server has two. The Scan Cache, the higher level, keeps the key/value pairs (cells) handed up by the SSTable layer. It helps when the same data is read again: a hit skips the Bloom filters, the index search and the block parsing. The Block Cache, the lower level, keeps SSTable blocks read from GFS. It helps when the next read is nearby, because a 64 KB block also holds the cell’s neighbours: other columns of the row and the next rows in key order. The 2006 benchmark shows it: one server did 4,425 sequential reads per second against 1,212 random ones, because each fetched block served the next 64 reads. Random reads waste most of each block, so random-read applications typically used 8 KB blocks. Both caches copy immutable SSTables, so a write never makes them wrong. Cloud Bigtable (2026) manages a block cache and a row cache for you; keys that keep related rows together still decide how well they work.

Caches do nothing for a first read, or for a cell that does not exist, yet that read must still check every SSTable. A Bloom filter (Burton Bloom, 1970) answers “definitely not” or “maybe”. It is a row of m bits, all 0, plus k hash functions. To add a key, set its k bits to 1; to ask, check the same bits. Any 0 means the key was never added. Here com.cnn.www sets bits 2, 9 and 13, and org.wikipedia.en sets 5, 9 and 14 (made-up hash values; Bigtable’s real filters test row/column pairs). com.example.www hits bit 3, still 0: definitely not, skip the file. com.cnn.www finds all its bits set: maybe, and the block read finds it. com.cnn.www/weather lands only on bits set by other keys: a false positive, costing one wasted block read but never a wrong answer. Bits only go from 0 to 1, so there are no false negatives. About 10 bits per key gives about 1% false positives, whatever the key length. A sealed SSTable’s filter never needs updating.

One read through every accelerator, in the natural order implied by where each one sits (the paper does not spell out the code). The client wants row com.cnn.www, column anchor:cnnsi.com, on a tablet with a memtable and three SSTables. The Scan Cache misses. The Bloom filters of SSTables 1 and 3 say “definitely not”; SSTable 2’s says “maybe”. SSTable 2’s in-memory block index picks block 5. The Block Cache misses, so the server fetches the 64 KB block from GFS, often a 10 ms disk seek: the only slow step. It keeps the block and the cell in its caches, merges with the memtable and replies: one disk read instead of three. Moments later the same cell is a Scan Cache hit, and a neighbouring column of the same row is a Block Cache hit. In 2006, Bloom filters were opt-in per locality group and tested row/column pairs; they cannot help range scans, because hashing scrambles order. Cloud Bigtable (2026) manages its filters for you.

9

A tablet server holds 10 to 1,000 tablets (2006 paper) and absorbs thousands of small writes a second. Every write is appended to a commit log in GFS before it reaches the memtable. One log per tablet looks tidy, but the paper rejects it for two reasons. Many files appended at once could cause many disk seeks under GFS, about 10 ms each. And group commit weakens, because each log batches only its own tablet’s writes. Toy numbers: 8,850 writes a second over 500 tablets is about 18 per tablet per second; with a 10 ms append (illustrative), a per-tablet append carries about one mutation, while one shared log carries about 89. So Bigtable keeps one commit log per tablet server, mixing every tablet’s mutations in arrival order. The payoff in the 2006 benchmark: 8,850 random and 8,547 sequential writes per second on one server, because at the log no write is random. Each server also keeps a spare log writer: if GFS stalls it switches, and sequence numbers drop any duplicates at recovery.

The shared log’s bill arrives when a server dies. The master spreads its tablets over many servers, and each new owner must replay its tablet’s records after the redo point, but those records are scattered through a log that mixes every tablet. Naively, each owner reads the whole log: in the paper’s example, 100 owners read it 100 times. Bigtable sorts the log first, by (table, row name, log sequence number). Table and row turn each tablet’s records into one contiguous run; the sequence number keeps changes to one row in commit order and puts duplicate copies side by side. The sort is spread out: the log is cut into 64 MB segments, each sorted in parallel on a different tablet server, with the master coordinating. Each owner then reads only its run in each sorted segment, a seek and a short read, and replays it. Here ts-63 has taken tablet D. Cloud Bigtable (2026) writes to a shared log on Colossus; how it replays that log is not published.

11

Not every move is a crash. The master also moves tablets on purpose, for example to balance load, and the old server is alive, so Bigtable can skip log replay. The tool is the minor compaction: write the memtable to GFS as a new SSTable and move the redo point past it. Compaction 1 runs while the tablet is still serving: it flushes the bulk of the memtable, the slow part, at no cost in availability. Then the server stops serving the tablet, so nothing new arrives, and compaction 2 flushes only the few writes that came in meanwhile, which is usually very fast. With nothing unflushed, the new server reads the tablet’s METADATA row, loads the SSTable indexes and starts serving, with no log replay and no data copied: the SSTables stay in GFS. The 2006 paper reports that a moved tablet is typically unavailable for under a second. Cloud Bigtable (2026): nodes hold no data, so rebalancing moves only metadata.

12

Bigtable never edits a file once it is written. An update is a newer version and a delete is a deletion entry; both go to the commit log and memtable, and later into a new SSTable. So the bytes a reader is looking at never change: the paper says reading SSTables needs no synchronization, and any number of threads can read one file at once. Apart from the log, which only grows at its end, only the memtable and the tablet’s METADATA row ever change. The memtable is the one structure that reads and writes both touch, so each memtable row is copy-on-write. A writer copies the row’s current version, edits the copy privately, then publishes it with one pointer swap (the paper gives this one sentence; the pointer swap is the standard technique). Scan A, started earlier, keeps reading v1; read B, after the swap, gets v2 with both new cells, never half of them. Readers never wait; writers to one row still take turns, and each change allocates a new version.

Immutability also makes splits and deletes cheap. When tablet T7 outgrows its split size (100–200 MB by default in 2006), the split is committed with a METADATA write of about 1 KB. No SSTables are rewritten: both children list the parent’s files and each reads only its own key range; later compactions give each child files of its own. Copying instead would rewrite about 200 MB, three replicas each, on the busiest tablet. Old files must go eventually, but eager deletion fails: a sibling may still need a shared file, and a crash can leave a half-written file nobody remembers. So the master runs mark-and-sweep (McCarthy, 1960) with METADATA as the roots: mark every SSTable some row lists, delete every other one. A shared file lives while any row names it; crash leftovers are swept. A deleted value is hidden at once, rewritten away by a major compaction, swept, then freed by GFS. Cloud Bigtable (2026): a compaction takes about a week on average.

What to remember

TEST YOURSELF

Q1. A Bloom filter says “maybe” but the cell is absent. A bug?

Answer: No: a false positive costs one wasted read, never a wrong answer.

Q2. Why two minor compactions before a planned move?

Answer: The slow one runs while serving; the tiny one leaves nothing to replay.

NEXT Deck 10 · Proof at Google

14

Five ideas to keep. Layout follows reading: locality groups give families read together their own SSTables, and row keys that sort similar data side by side let the compressor find repeats. Compression is per block, so a random read pays for one block. Each accelerator matches a pattern: the Scan Cache for the same cells again, the Block Cache for neighbouring cells, Bloom filters for cells a file does not have. One commit log per server keeps writes sequential; recovery sorts it in parallel 64 MB segments, and planned moves avoid replay with two minor compactions. Immutability gives lock-free reads, copy-on-write rows, splits that share files and mark-and-sweep clean-up. In Cloud Bigtable (2026) the service manages layout, compression, caches and filters; your levers are row keys, column families and read filters. A third question to try: why did Webtable get 10 to 1 when gzip gets 3 or 4 to 1? One host’s pages sit side by side, and pass 1 finds their long shared boilerplate.
