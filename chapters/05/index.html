This deck is about the calls a program makes to Bigtable: its API (application programming interface). The API is small on purpose. The 2006 paper describes it in about one page: create and delete tables and column families, write and delete values, look up one row, scan a range of rows, plus a few power tools: single-row transactions, integer counters, batched writes across rows, Sawzall scripts that run inside the servers, and wrappers for MapReduce jobs. Every idea survives in Cloud Bigtable, mostly under new names, and each slide maps the 2006 call to today's Data API and Python client. The running examples are the paper's Webtable (one row per web page, keyed by the reversed URL) and a fictional payments ledger whose row key is acct#<account>#<reverse timestamp>, with column families txn and risk. Colours are fixed across the series: amber for writes, teal for reads, violet for the control plane, cobalt for "look here".

A payments platform. Creating the table is a rare admin call; thousands of payments a second go straight to their tablet servers.

2

Bigtable's calls fall into two groups. Admin calls change the shape of the data: create or delete a table, create or delete a column family, and change metadata such as access rights, which in 2006 were set per column family. In the paper's design the master handles these schema changes, and the schema and access lists are stored in Chubby, so they are control-plane work (violet). Data calls change or read rows: writes and deletes, lookups and scans, single-row transactions and counters, batched writes and, in 2006, Sawzall scripts. They go straight to the tablet server that owns the row, once the client library knows where the row lives. The master never sits on the data path. Families are few and rarely changed; columns inside a family need no admin call at all, because writing a new qualifier creates it. Cloud Bigtable (2026) splits this into an Admin API and a Data API, and replaces per-family access lists with IAM permissions on projects, instances, tables and views.

IN THE REAL WORLD

Updating a contact card

A customer changes phone and email together. Both cells are in one row, so one mutation carries both.

Support sees the old pair or the new pair, never a mix.

ONE ROW, ONE MUTATION

row cust#1042

set contact:phone

set contact:email

3

Every write is a mutation: a list of changes to one row. In the paper's C++ client it is a RowMutation: create it for one row key, queue operations such as "set this column" and "delete that column", then apply it. The paper's Figure 2 does what the slide shows on the Webtable row com.cnn.www: it adds an anchor from www.c-span.org and deletes the anchor from www.abc.com. Apply is atomic: a reader sees the row before or after, never one of the two half-way states in red, and no crash can leave the row stuck in one. Why is that cheap? Exactly one tablet server serves a row at a time. In the paper's design the whole mutation arrives in one request, is appended to the commit log as one record, then applied to memory; a crash before the log write loses all of it, a crash after it is repaired by replaying all of it. Cloud Bigtable's docs say less about the inside; the guarantee is the same: MutateRow, up to 100,000 mutations (classic Python: direct_row, set_cell, delete_cell, commit()).

4

Writing many rows one request at a time wastes round trips, so the client library can batch writes across rows. But a batch is not a transaction. The library routes each row to the server that owns it, and each server logs and applies its rows on its own, without waiting for, or even knowing about, the others. In the picture, server B has just stopped serving the tablet that holds row 2, because the master is moving it, so B rejects that row and writes nothing. The batch comes back OK, FAILED, OK. Rows 1 and 3 stay written; nothing is rolled back. Your code retries only row 2, once the library has found the tablet's new server. Making a batch all-or-nothing would need a distributed protocol such as two-phase commit, with extra round trips on every write; the paper's authors chose not to pay that price. In Cloud Bigtable this is MutateRows: each entry is atomic, the request is not. The classic Python mutate_rows returns one status per row: ignore that list and you silently drop rows.

IN THE REAL WORLD

A queue delivers a payment twice. With the payment time as the cell’s timestamp, the second delivery just rewrites the same cell.

5

A cell is identified by row, family, qualifier and timestamp. Write the same four coordinates twice and the second write replaces the first; write with a new timestamp and you add a version. That rule decides whether a resend is harmless. On the left the timestamp comes from the event itself, the payment time, so a resend lands in the same cell. On the right no timestamp is given: the classic Python client then asks the server to stamp each arrival with its own clock, so a resend becomes a second version. Resends happen more than you think: a timeout means "no answer", not "no change", and queues can deliver a message twice. As of 2026, Cloud Bigtable's client libraries retry reads, and writes whose cells all have fixed timestamps, automatically; for a batch they resend only the failed entries. Check-and-mutate and increments are never retried for you, because doing them twice is not the same as doing them once. Cloud Bigtable takes timestamps in whole milliseconds; the 2006 paper used microseconds.

6

Reads come in two shapes. A lookup fetches one row by its key. A scan walks a contiguous range of keys in sorted order. Both are cheap because rows are stored sorted by key: the server reads only the rows inside the range, which usually sit in one tablet or a few neighbours. The paper uses one abstraction for both, the Scanner. In Cloud Bigtable both are ReadRows, which takes row keys and row ranges written [start, end): start included, end excluded, so the row acct#8815#... on the slide is not read. There is no "prefix" option: a prefix becomes a range whose end is the prefix with its last byte plus one. "#" is byte 0x23 and "$" is 0x24, so acct#8812# becomes [acct#8812#, acct#8812$). End every prefix with its delimiter: acct#8812 without the "#" would also return account 88120. Because the payment key ends in a reverse timestamp, "my last 50 payments" is just this prefix scan with limit=50, and the newest come first. Python: read_row(key), read_rows(start_key=..., end_key=..., limit=50).

IN THE REAL WORLD

Only the pages you need

WATCH OUT

Filters cut what is sent, not what is read

7

A filter is a small program attached to a read. The tablet server runs it on each row and sends back only the cells that survive. Filters in a chain work like a pipeline: each sees only what the previous one kept. Here the first keeps the txn family and the second keeps only the newest version of each column, so 3 of the row's 6 cells travel to your app. The paper's 2006 Scanner could narrow a scan the same ways: by family, by a pattern over column names, by timestamp range, and all versions or fewer. Today's names are FamilyNameRegexFilter, ColumnQualifierRegexFilter, TimestampRangeFilter and CellsColumnLimitFilter; regexes use RE2 syntax and a whole filter may be at most 20 KB. Cloud Bigtable returns every stored version unless you limit it, which is why most code adds CellsColumnLimitFilter(1). The catch: filters save network bytes and client work, not the server's reading. The server still assembles every row in the range before filtering, so only the row key range limits that work; a row-key regex with no range scans the whole table.

8

Some updates depend on what is already there: "mark the payment SETTLED only if it is still PENDING". If each worker reads the row, checks in its own code and then writes, two workers can both read PENDING and both settle. Check-and-mutate moves the check onto the server. You send a test (a read filter) and two lists of changes; if the test matches, the server applies the first list, otherwise the second, as one atomic step on that row. Operations on one row behave as if they ran one after another, so A settles the payment, and B's test then sees SETTLED and takes the harmless false branch. The paper calls this a single-row transaction; Cloud Bigtable's call is CheckAndMutateRow (conditional_row in the classic Python client). Three rules: one row only; it needs an app profile with single-cluster routing and single-row transactions allowed; and it is never retried automatically, so after a timeout read the row before trying again. In the test, keep only the newest version before checking the value, or an older PENDING version can match.

9

Counting has the same race. If two clients each read 41, add one in their own code and write 42, the second write replaces the first and one page view vanishes: a lost update. Read-modify-write fixes it by sending the arithmetic instead of the answer. Each client sends "add 1"; the one server that owns the row reads the latest value, adds, writes a new cell and returns the result, one request at a time, so 41 becomes 42 and then 43. The 2006 paper says cells can be used as integer counters; Cloud Bigtable's call is ReadModifyWriteRow (append_row plus increment_cell_value in the classic Python client). Details that bite: the cell must hold an 8-byte big-endian integer, and a missing cell counts as 0. Like check-and-mutate it needs single-cluster routing and is never retried for you, because an increment applied twice counts twice. Keep the raw events so a counter can always be recomputed. (The stats:views family is a made-up example.)

IN THE REAL WORLD

A stadium with one open ticket window

CLOUD BIGTABLE, SINCE 2024

Aggregate column family

AddToCell adds with no read first; sums merge correctly, even across clusters.

10

Atomic increments make a correct counter, not a fast one. Every increment of one counter lands on one row, so on one tablet server, which applies them one at a time. Splitting cannot help, because the smallest piece Bigtable can move is a single row. A "total payments today" cell hit 50,000 times a second becomes a hotspot: one overloaded server while the rest idle. (The bars are an illustration, not measurements.) The usual fix is to spread one logical counter over several rows, say 16 shards with a shard number in the key, and add them up when reading. Cloud Bigtable added a second fix in 2024: aggregate column families (sum, min, max and approximate distinct count). You send AddToCell inside a normal write, there is no read before the write, and the values merge correctly even across clusters, so the docs now prefer them to increments for counters. Cloud Bigtable's docs also advise against read-modify-write at high volume. Remember too that increments are not idempotent: a blind retry after a timeout can count twice.

11

In 2006 Bigtable offered two ways to process lots of data. Sawzall scripts ran inside the tablet servers' own processes, next to the data: they could transform, filter and summarise, but could not write back into Bigtable, and only small totals crossed the network. MapReduce wrappers let a table be both the input and the output of a batch job. Batch jobs and user traffic shared the same tablet servers and machines. Cloud Bigtable runs no customer code on its servers. The server-side work you can ask for is filters and GoogleSQL: read-only SELECT queries, in preview from August 2024 and generally available since April 2025. Bulk processing moved to Dataflow (Apache Beam), Spark, Hadoop through the HBase client, and BigQuery. Data Boost runs heavy read jobs on separate serverless compute so they do not slow the nodes serving your app; it became generally available in early 2025, is read-only, and only guarantees to see data written more than 35 minutes earlier. The Analytics example is from section 8 of the paper; sizes are from its Table 2.

IN THE REAL WORLD

A stock-take split by aisle. Each person counts one aisle at once; a miscount redoes only that aisle.

THEN VS NOW

2006: MapReduce wrappers split tables by row range. Today Dataflow and Spark do it for you.

12

One read_rows() over a whole table is one long stream, read tablet by tablet by a single worker, and it can run into the client's overall read deadline (600 seconds by default in 2026). To read in parallel you need cut points that split the table into pieces of similar size. SampleRowKeys returns exactly that: a sorted list of row keys that divide the table into contiguous sections of roughly equal size, each with an estimate of how many bytes are stored before it. Bigtable can answer cheaply because it already tracks the table as tablets, which are row ranges; think of the cuts as approximate tablet boundaries. Four cut keys make five half-open ranges that together cover every row exactly once. Give the ranges to a pool of workers: they run in parallel, the job takes about as long as its slowest piece, and a failed piece is read again on its own. Making more pieces than workers lets fast workers pick up the slack. The cut keys on the slide are made up.

# record one payment, atomically

row = payments.direct_row(key)

row.set_cell("txn", b"status",

    b"PENDING", timestamp=paid_at)

row.commit()

 

# the account’s last 50 payments

    start_key=b"acct#8812#",

    end_key=b"acct#8812$",

    limit=50)

 

# settle it only if still PENDING

crow = payments.conditional_row(

    key, filter_=still_pending)

crow.set_cell("txn", b"status",

    b"SETTLED", state=True)

crow.commit()

13

This is the whole API on one page, in the classic Python client (package google-cloud-bigtable). The core Data API calls are easy to remember as "2 writes, 1 read, 2 transactions, 1 map": MutateRow and MutateRows; ReadRows; CheckAndMutateRow and ReadModifyWriteRow; and SampleRowKeys. Admin calls (tables, families, GC rules) go through a separate Admin API; in Python, create the client with admin=True. The code on the right is the payments app: it records a payment as one atomic row with an explicit timestamp, so a resend is harmless, then reads the account's last 50 payments with a prefix scan, then settles the payment only if it is still PENDING (still_pending is a filter chain: family txn, column status, newest version only, value PENDING). The newer data client (google.cloud.bigtable.data) offers the same calls as mutate_row, bulk_mutate_rows, read_row, read_rows with a ReadRowsQuery, check_and_mutate_row, read_modify_write_row and sample_row_keys. Create one client per process and reuse it, and name an app profile for each workload. Names and defaults change between versions (these are as of October 2026); check the reference for yours.

RECAP

What to remember

1

Admin calls shape the table; data calls go straight to the server that owns the row.

2

One row: all or nothing. A batch can half-succeed; fixed timestamps make retries safe.

3

Reads are lookups or key ranges. Filters trim what is sent, not what is read.

4

Check-and-mutate and increments: one row, correct, never auto-retried, hot if shared.

5

Big jobs: split with sample_row_keys, or use Dataflow, Spark or BigQuery with Data Boost.

TEST YOURSELF

Q1. A batch of 1,000 writes returns 3 FAILED. What state is the table in?

Answer: 997 rows are written and stay written. Retry only the 3.

Q2. Two workers settle one payment with check-and-mutate. What happens?

Answer: The first settles it; the second sees SETTLED and takes the false branch.

Q3. Will a value filter make a billion-row scan fast?

Answer: No. The server still reads every row in the range.

14

The API is small because the data model is small: shape the table, change one row, read a row or a range, plus counters, batches and bulk processing. One row: anything, atomically. Many rows: each one on its own. If you remember one thing about writes, make it the timestamp rule: a fixed timestamp turns a resend into an overwrite. If you remember one thing about reads, it is that the row key range decides how much the server reads, and filters only trim the answer. Still missing in 2026: multi-row transactions and joins.
