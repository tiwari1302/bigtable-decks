Architecture: Finding and Owning Data

Who serves which rows, how a client finds them, and why a tablet never has two owners

DECK 07 · Inside the machine

The three parts, and why your data never passes through the master

How a client finds any tablet in three hops, then remembers

How Chubby locks keep exactly one owner per tablet

This deck opens up the machine. Deck 06 introduced the building blocks: GFS, SSTables, Chubby and the cluster manager. Here they come together as Bigtable's three moving parts. You will see why the master can stay off the data path, how a table that starts as one tablet ends up as many tablets spread over many servers, how a client finds the one server holding a row in three hops from a cold start without asking the master, and how lock files in Chubby make sure a tablet never has two owners, even when the network breaks. Everything here describes the 2006 paper's design (section 5). Cloud Bigtable keeps the same shape but hides the internals; where it differs, the notes say so.

The picture is the 2006 architecture. Read it by colour: amber and teal arrows carry row data, violet arrows are control traffic. A client library is linked into every application. It works out which tablet server holds a row and talks to that server directly. Tablet servers (10 to 1,000 tablets each in 2006) do the actual reads and writes, and every file they use, commit logs and SSTables, lives in GFS. One master per cluster decides which server serves which tablet, but no amber or teal arrow touches it. Its work grows with the number of tablets and servers, not with the number of requests, which is why a single master ran clusters of more than 500 tablet servers. Chubby holds tiny critical files: the master lock, the root tablet's location, one lock per server. Example: a payments API asks for the last 50 transactions of account 8812; its client library sends the scan straight to the server holding acct#8812#: usually one round trip. Cloud Bigtable calls tablet servers nodes and keeps the data in Colossus.

The master has five duties, all control-plane work: Garbage-collect SSTable files in GFS that no tablet uses, Balance load across tablet servers, Assign tablets to servers, Detect servers joining and dying, and apply Schema changes such as new tables and column families. Mnemonic: Good Bosses Assign Duties Sensibly. What it never does: carry row data, answer "where is row X?", or split tablets. So when the master crashes, tablet assignments do not change (paper section 5.2). Tablet servers keep their own locks and keep serving, and clients keep finding tablets through their location cache and the METADATA table. Reads and writes carry on. Only control work waits until the cluster manager starts a new master, which takes the master lock in Chubby so there is never more than one. A common misconception is that one master is a single point of failure for the cluster. It is one for administration, not for traffic. In Cloud Bigtable, a per-zone primary process balances, splits and merges tablets.

4

A new table is a single tablet covering every row key, so every write lands in it and it grows. In 2006 the default tablet size was about 100 to 200 MB. Once a tablet passes that, the tablet server holding it, not the master, picks a split row key and cuts it in two (the paper does not say how the key is chosen; one near the middle of the data gives even halves). Both halves keep reading the parent's SSTables in GFS, so a split copies no data. The server commits the split by writing the new tablet into the METADATA table, then tells the master. If that message is lost, nothing breaks: the next server asked to load the old tablet sees in METADATA that it covers only part of the range and reports the split. The master then balances load by moving tablets; in the 2006 benchmarks a moved tablet was typically unavailable for under a second. The master starts the other changes: creating a table, deleting one and merging two tablets.

5

Why keep tablets small? The paper gives the size, 100 to 200 MB by default in 2006, but not the reasoning; the reasons follow from the rest of the design. Moves are cheap: a server taking over a tablet reads its METADATA row, loads the SSTable indexes and replays recent log entries, and the index part grows with tablet size. Balancing is fine-grained, because the master can only shed load one whole tablet at a time. And recovery is parallel. The picture uses illustrative units: each server carried 6 units when ts-4 died. As two big tablets, its load can only go to two servers, which go over capacity while the third gets nothing. As six small tablets, every survivor takes two. At real scale, a server with 600 tablets dying in a 101-server cluster costs each survivor about 6 tablet loads, done in parallel. Smaller is not free: every tablet needs a METADATA row of about 1 KB, its own memtable, files and compactions, and every boundary is one more hop for a scan.

How does a client find the one server, among hundreds, that serves a row, without asking the master? Bigtable stores tablet locations in a Bigtable table called METADATA, one row per tablet. METADATA is split into tablets too, so it is indexed by its first tablet, the root tablet, which never splits. The root tablet's location sits in one small Chubby file with a fixed, well-known name. A client with an empty cache walks it: trip 1 reads the Chubby file (root is on ts-17); trip 2 asks ts-17 which METADATA tablet covers (Webtable, com.cnn.www): M-2 on ts-42; trip 3 asks ts-42, which answers W-2 on ts-09. Then the real read goes to ts-09. The client caches every answer. Chubby stores only the root's location, not the root itself; the root and METADATA tablets are ordinary tablets on ordinary servers. The paper compares the shape to a B+ tree, and DNS works the same way. Mnemonic: Cats Rarely Miss Us. Server and tablet names are illustrative. Cloud Bigtable hides all of this behind its frontend servers.

Inside METADATA, each row key is the tablet's table id plus its end row, the last row key the tablet covers. The tablets of a table never overlap and leave no gaps, so the tablet holding row r is the first METADATA row whose key is at or after (table, r). Every row before it ends too early to contain r. A sorted map answers "first key at or after X" natively: it is the same seek a scan uses to find its starting point, and on in-memory data it is a quick binary search. Putting the table id first keeps all of a table's tablets together. Each METADATA row keeps about 1 KB in memory; besides the location it lists the tablet's SSTables and commit-log redo points, used when a server loads the tablet, and an event log. In the example, com.cnn.www sorts after com.apple.www and before com.cnn.www/world, so W-2 holds it. Names, keys and servers are illustrative. HBase keys its catalog by start row instead and looks for the last key at or before the target; both work.

Of the three levels, only two are wide indexes: the root tablet and the METADATA tablets. The Chubby file holds one location. The paper gives two inputs: about 1 KB per METADATA row and a 128 MB limit on METADATA tablets. In powers of two, 128 MB is 2²⁷ bytes and 1 KB is 2¹⁰ bytes, so one METADATA tablet holds 2¹⁷ = 131,072 locations. The root never splits, so it lists up to 2¹⁷ METADATA tablets, and each of those lists up to 2¹⁷ user tablets: 2³⁴, about 17.2 billion tablets. At 128 MB per user tablet that is 2⁶¹ bytes, about 2 exbibytes. For scale, the largest table in the paper, the 800 TB Crawl table (Table 2), would use roughly 1/3,000 of that ceiling. With only one index level, the root could list just 2¹⁷ tablets, about 16 TiB, too small even for Crawl; a third index level would add a round trip to every cold lookup. That comparison is our arithmetic; the paper states only the result. Cloud Bigtable publishes no equivalent numbers.

9

Each application process keeps a location cache from tablet ranges to servers. Warm: the cache knows the server, so the read goes straight there with zero extra round trips. In a running system almost every request looks like this. Cold: a freshly started process knows nothing and walks all three levels, Chubby, root, METADATA, before the read. Stale: nobody tells a client when a tablet moves, so stale entries are found only on a miss. The client then climbs up one level and asks again, only as far as it must. Usually only the user tablet moved: one miss plus one METADATA read, 2 extra trips. In the worst case all three cached levels are wrong: three misses walking up, then Chubby, root and METADATA walking down, the paper's "up to six". Lazy correction wins because requests are frequent and moves are rare. Prefetching helps too: each METADATA read also returns neighbouring tablets, and locations sit in memory, so lookups never touch GFS. The paper gives the 3 and the 6; the 2 is the standard reading of it.

The rule is that each tablet is assigned to one tablet server at a time. If two servers served the same tablet, each would keep its own memtable and commit log, and the row would end up with two histories (split brain). Bigtable enforces the rule with Chubby. When a tablet server starts, it creates a uniquely named file in Chubby's servers directory and takes an exclusive lock on it. The master watches that directory to discover new servers. The lock lasts only as long as the server's Chubby session, kept alive by KeepAlive messages. The server enforces three rules on itself: serve only while holding the lock; if the lock is lost, stop serving at once and keep retrying while the file exists; if the file is gone, exit for good. A server shut down on purpose releases its lock so its tablets can move quickly. A restarted process registers under a new file name, so it is never mistaken for the old one. Cloud Bigtable keeps the one-node-per-tablet rule but does not document its membership machinery.

11

Missed status checks are ambiguous: the server may have crashed, or only its link to the master may be broken while it still serves clients. So the master never reassigns on missed checks. It asks Chubby for an exclusive lock on the server's file. Getting it proves that Chubby works and the server's session has ended, so it has already stopped serving. The master then deletes the file. That is the fence: if the server comes back, it finds no file and kills itself. Only then are its tablets reassigned, loaded by other servers from GFS. If the master cannot get the lock, the server is still licensed and its tablets are left alone (the paper does not spell out this branch). Timing makes it safe: the server's own pessimistic lease timer runs out no later than Chubby's copy, so the old owner stops before anyone else can start. This ordering is our reading of the paper and Chubby's lease rules; the paper gives no proof. The price is a short window with no owner, while clients retry.

12

A new master starts with an empty ledger, because the old master kept the assignment only in memory. It rebuilds it from three sources that survive any master crash: Chubby, the tablet servers and the METADATA table. The paper lists four steps. Lock: grab the unique master lock in Chubby, so two masters never run at once. List: scan the servers directory to find the live tablet servers. Ask: ask each one which tablets it already serves. Scan: read METADATA to learn the full set of tablets; any tablet nobody reported is unassigned and gets a load request. One rule comes before the scan: if nobody reported the root tablet, the master assigns it first, because METADATA cannot be read without it. Mnemonic, with R for that rule: Late Librarians Always Read Shelves. The idea behind it: the master's memory is only a cache of facts stored elsewhere, so a master crash costs a restart and nothing else. A master that loses its own Chubby session kills itself.

Q1. The master crashes. Do reads and writes stop?

Answer: No. Clients use their cache and METADATA; only admin waits.

Q2. Why delete a dead server’s file?

Answer: It is the fence: no file, no serving, never two owners.

13

Five ideas to keep from this deck. First, the split of roles: clients route themselves, the master only decides, tablet servers do the work, and all data lives in GFS. Second, tablets are the unit that splits and moves, and keeping them small (100 to 200 MB in 2006) makes moves cheap and recovery parallel. Third, the three-level lookup through Chubby, the root tablet and METADATA, made cheap by caching: 0 trips warm, 3 cold, up to 6 stale. Fourth, Chubby locks give each tablet at most one server, and the master fences a silent server by taking its lock and deleting its file before reassigning anything. Fifth, the master's memory is only a cache, so a new master rebuilds it with Lock, List, Ask, Root, Scan. Next deck: what a tablet server does with each write and read.
