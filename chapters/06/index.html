Bigtable is not one program that does everything. The 2006 paper (section 4, "Building Blocks") says it stands on other Google infrastructure: GFS, a distributed file system that holds its log and data files; SSTable, the sorted file format those data files use; Chubby, a small lock service that settles who is in charge; and a cluster management system that starts, places and restarts its processes. MapReduce jobs then use whole tables as their input and output. This deck opens each of those parts in turn, with one picture per idea and an everyday example for each. The pattern to watch for is the same in every part: a small control piece that knows "where" or "who", kept off the path where the bytes travel. Where Cloud Bigtable (2026) differs from the 2006 design, the slides say so: Colossus has replaced GFS, and the public docs do not describe a Chubby equivalent.

Read the picture from the middle. Bigtable itself is three things: a client library linked into every application, one master that assigns tablets, and many tablet servers that serve reads and writes. Underneath sit the parts it does not build itself. Tablet servers store their two kinds of files in GFS: commit logs and SSTables (sorted, never-edited data files). Chubby, a lock service of typically five replicas, holds tiny files: the master holds its lock there, and a client with an empty cache finds the root tablet's location there. At the bottom, a cluster management system (named Borg in 2015) starts Bigtable's processes on machines shared with other jobs and restarts them when machines die. On top, MapReduce batch jobs read whole tables and write results back as row mutations. The design consequence: a tablet server holds nothing that exists only on its own machine, so any server can crash or be moved without losing data. Cloud Bigtable keeps the same split, with Colossus in place of GFS.

GFS, the Google File System (2003 paper), spreads files over the disks of many machines but looks like one set of named files. It has three roles. One master per cell keeps all metadata in memory: file names, the list of chunks in each file, and where each chunk's copies are. Hundreds or thousands of chunkservers hold the bytes: every file is cut into fixed 64 MB chunks, each named by a 64-bit handle and stored as an ordinary Linux file. By default each chunk has three replicas on three chunkservers in different racks, because a rack shares one switch and one power circuit; a rack failure then costs each chunk at most one copy. The master learns what each chunkserver holds through regular HeartBeat messages, and when a chunkserver dies it re-copies the scarcest chunks first from surviving replicas. Big chunks keep the map tiny: under 64 bytes of metadata per chunk, so a petabyte needs only about 1 GB of master memory. In the picture, chunk 2ef0 (highlighted) has one copy in each rack.

This is how a tablet server (here acting as a GFS client) reads part of an SSTable file, step by step as the GFS paper describes it. Step 0 needs no network: chunks have a fixed size, so the client library turns a byte offset into a chunk index by itself (byte 150,000,000 divided by 64 MB is chunk 2, at offset 15,782,272 inside it). Step 1: it asks the master for that chunk. Step 2: the master answers with the chunk handle and the three replica locations (and may add the next chunks for free); the client caches all of it. Step 3: the client asks the nearest replica for the byte range. Step 4: that chunkserver checks its checksums (one per 64 KB block) and sends the bytes. Later reads of the same chunk skip the master entirely. File bytes never pass through the master, which is why one master can serve thousands of machines. Bigtable copies the pattern: clients find a tablet once, then talk to its tablet server directly; the Bigtable master never carries data.

5

Because a tablet's whole persistent state lives in GFS, nothing a tablet server holds is the only copy. Follow tablet T, say the payments rows acct#8800 to acct#8899. Server A appends T's writes to its commit log in GFS and reads T's SSTables from GFS; its memtable, block indexes and caches are working copies. A crashes and that memory is gone, but every acknowledged write is in the commit log, which GFS holds three times. The master notices and asks server B to load T. B reads T's METADATA row (its SSTable list and the redo point in the log), opens the same SSTable files, loads their indexes and replays the log records after the redo point into a fresh memtable. Bytes copied from A to B: none. The same fact makes load balancing and splits cheap. A common misconception: the three copies are GFS replicas of files, not three tablet servers; exactly one server serves a tablet at a time. Cloud Bigtable works the same way on Colossus, where nodes hold only pointers to their tablets.

6

GFS's single master became the limit: all metadata in one machine's memory, every metadata operation through it, and slow fail-over. Colossus, its successor, keeps the GFS pattern (metadata on one path, bytes flowing directly between clients and disk servers) but spreads the metadata work. Google's 2021 description names five parts, remembered as "Can Curious Cats Dig Burrows?": the Client library (chooses plain copies or RAID-like encodings), Curators (the control plane, scaling out), Custodians (background repair and rebalancing), D file servers (the disks) and Bigtable, which stores the file metadata. That makes a loop: Bigtable stores its files in Colossus, and Colossus keeps its metadata in a much smaller Bigtable. It ends because metadata is about 1/10,000 of the data it describes: 100 PB needs about 10 TB, then about 1 GB, then about 100 KB, small enough for Chubby. That is a 2017 sizing argument; Google has not published the exact production layering. Cloud Bigtable (2026) stores tablets on Colossus in SSTable format, and its nodes hold only pointers, so adding nodes copies no data.

An SSTable is the file format for all tablet data on disk (only the commit log differs). The paper calls it a persistent, ordered, immutable map from keys to values, both arbitrary byte strings, with two operations: look up one key, and iterate over a key range. Inside, sorted entries are packed into blocks of typically 64 KB (configurable in 2006). After the last block comes the block index: one entry per block, best pictured as the block's first key and its position. The index goes last because the file is written in one sequential pass; only then is the index complete. When a tablet server opens the file, it reads the index into memory and keeps it there: for a 128 MB file that is 2,048 entries, roughly 200 KB (derived, assuming ~100-byte entries). "Sorted, Sealed, Signposted, Stored" sums up what each word buys. Keys and offsets in the picture are illustrative. Cloud Bigtable (2026) still stores tablets in SSTable format; block size and compression are managed for you.

A point lookup has two parts. First, a binary search over the block index, which is already in memory. To find acct#2650: b3 starts with acct#3861, which is bigger, so look left; b1 starts with acct#1290, smaller, so look right; b2 starts with acct#2577 (smaller) and b3 with a bigger key, so the key can only be in b2. Three comparisons, no disk. Second, one read: fetch block b2 (64 KB) from GFS, then walk its sorted entries in memory until acct#2650 turns up. Scale the toy up to a real 128 MB file with 2,048 blocks: about 11 comparisons in RAM (roughly a microsecond) and still exactly one read, around 10 ms on 2006 spinning disks, so the read costs about ten thousand times more than the search (derived from 2009 latency figures). That is why the design spends memory on the index. Two cautions: a missing key usually still costs a read (Bloom filters, deck 09, fix that), and a tablet read may consult several SSTables plus the memtable (deck 08).

Chubby is a small, highly available lock service that also stores tiny files (Mike Burrows, 2006). One deployment, a cell, is typically five servers called replicas, in different racks. They use Paxos to elect one of themselves as the Chubby master, which needs a majority of votes. Every client request goes to the master. A write is sent through Paxos to all replicas and is committed once a majority, three of five, holds it; reads are answered by the master alone, which is safe while its master lease holds. The cell works while any three replicas run and can talk, so it survives two failures, and any two majorities of five share a replica, so no decision is quietly contradicted. In the picture R4 and R5 are down, yet the write commits on R1, R2 and R3. A failed master is replaced in seconds (4 s and 6 s reported, up to 30 s). Clients hold sessions: here the Bigtable master holds the master lock and tablet server ts-17 its own server file (names illustrative).

10

A Chubby session links one client process to the cell; the client's locks, handles and cached data are valid only while the session is. The session has a lease, a stretch of time in which the Chubby master promises not to end it. KeepAlive calls keep it going; each reply extends the lease, by 12 seconds by default. The client also keeps a cautious local lease. If that runs out without a reply, the session is in jeopardy: the library empties its cache, blocks the application's Chubby calls and keeps trying for a 45-second grace period. If a KeepAlive gets through, the session is safe and the application saw only a delay. If not, the session expires and every lock goes with it. For Bigtable that is the safety net: a tablet server that loses its lock stops serving its tablets, and a master whose session expires kills itself. Chubby master elections usually take seconds (4 s and 6 s reported, up to 30 s seen), so a fail-over normally fits inside the grace period and no tablet moves.

The paper lists five uses of Chubby; learn them as "My Big Dog Sleeps Alot". M: at most one active master; the master holds an exclusive lock on a master-lock file and writes its address into it. B: the bootstrap location; a Chubby file names the server holding the root tablet, level 1 of the three-level lookup (deck 07). D: discover tablet servers and finalize their deaths; each server creates and locks its own file in a servers directory, and to declare a server dead the master takes that lock and deletes the file, so the server can never serve again. S: schema, the column families of each table. A: access control lists, checked on reads and writes from Chubby's consistent client cache, almost always a hit. Everything is tiny: in one surveyed cell 90% of files were under 1 KB, with a 256 KB limit. The root tablet itself is not in Chubby, only its location. File names here are illustrative. Cloud Bigtable's docs do not mention Chubby; access control there is IAM.

The paper is blunt: if Chubby is unavailable for long, so is Bigtable. To measure the cost, the authors looked at 14 Bigtable clusters using 11 Chubby cells and counted the server-hours in which some Bigtable data was unavailable because of Chubby. Average: 0.0047% of server-hours. Worst cluster: 0.0326%. Scaled to a year of 525,600 minutes, that is about 25 minutes on average and about 171 minutes (2 h 51 min) for the worst cluster. Three cautions: the paper does not say how long it measured, so "per year" is our scaling for intuition; the metric counts hours in which some data was unavailable, not whole-cluster outages; and it covers only Chubby-caused problems. The comparison bars are the yearly downtime budgets of 99.99% (about 53 min) and 99.9% (about 8 h 46 min) availability. Why so small? Chubby sits beside the data path, not on it: clients read the root location only with an empty cache, access checks hit the local cache, and KeepAlives run in the background.

Under Bigtable sits a cluster management system (named Borg in 2015; the 2006 paper does not name it) with four jobs: Place processes on machines, Share each machine, Replace processes when machines fail, and Watch machine health. One shared machine may run a chunkserver, a tablet server, a MapReduce worker and another team's job. Sharing saves hardware (Borg's 2015 paper: keeping production and batch apart would need 20-30% more machines in its median cell) but brings noisy neighbours. When machine A loses power, Borg starts a fresh tablet server, ts-9, elsewhere. Ownership is not Borg's call: the Bigtable master reassigns ts-3's tablets only after taking ts-3's Chubby lock and deleting its file, and the new owners load them from GFS. Over Bigtable, MapReduce uses whole tables as input and output: tablets are ready-made splits (one map task per row range), the shuffle groups values by key, and each reduce result is written back as an atomic row mutation, which should be idempotent because a task can run twice. In Cloud Bigtable, Dataflow, Spark and BigQuery play this role.

TEST YOURSELF

Q1. A tablet server crashes. What data is copied?

Answer: None: its successor reopens the same GFS files.

Q2. Why is an SSTable lookup one disk read?

Answer: Its RAM index names the one block.

Q3. Three of five Chubby replicas fail. Then?

Answer: No majority; if that lasts, Bigtable stops.

NEXT Deck 07 · Architecture: finding and owning tablets

14

Five ideas to keep. First, Bigtable keeps nothing irreplaceable on a tablet server: commit logs and SSTables live in GFS (Colossus today), 64 MB chunks with three replicas across racks, so tablets move by reopening files. Second, the "ask where, then go direct" pattern: GFS clients get locations from the master once and read chunkservers directly, and Bigtable clients do the same with tablet servers. Third, an SSTable is a sorted, immutable file with a block index at the end; with the index in RAM, a lookup is a binary search plus one block read. Fourth, Chubby is a five-replica lock service that needs a majority of three; its tiny files hold the master lock, the root location, the server list, schemas and ACLs, and a session that expires takes its locks with it. Fifth, the cluster manager (Borg) runs the processes, and MapReduce uses tables as batch input and output. Next deck: how these parts combine into Bigtable's architecture.
