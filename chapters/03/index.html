Storage Engine Basics

How a database makes writes fast, crash-safe and quick to find

DECK 03 · Foundations

Why memory beats disk, and order beats jumping around

How a log makes a write survive a crash

How an LSM-tree buffers, flushes and merges

How a sorted file finds any key with one read

A storage engine is the part of a database that decides how data is laid out in memory and on disk, and how it is written and found again. Every storage engine answers three questions: where does a new write go first, how does it survive a crash, and how do you find it again quickly among billions of others? This deck builds Bigtable's answers from the hardware up. Most of them follow from one fact: writing bytes in order is cheap, and jumping around is expensive. From there we meet the write-ahead log, group commit, the two families of storage engines (B-trees and LSM-trees), sorted files with an index, the benefits of files that never change, and short previews of compression, caching and Bloom filters. The last content slide shows that Bigtable is an LSM-tree per tablet, spread over many machines. Later decks (06, 08, 09) open each part in detail. The running example is a fictional payments platform.

Computers keep data in layers; each layer down is bigger, cheaper per byte and slower. Latency is the time one operation takes. The times come from the list Jeff Dean of Google presented in 2009 (the SSD row, a random 4 KB read, from a widely shared 2012 version). The bars use a log scale: each labelled tick is a factor of 1,000. The right-hand column stretches time so one nanosecond lasts one second: a RAM read becomes a cup of tea, a disk seek a school term. The fridge, the corner shop and another city make the same point with groceries. Three facts to carry forward. RAM is about 100,000 times faster than a disk seek (100 ns against 10 ms). RAM forgets everything in a crash or power cut; SSDs and disks keep their contents. And a round trip inside a datacenter (0.5 ms) beats a disk seek, which is why Bigtable can keep its files on other machines, in GFS. Hardware has improved since, SSDs most of all: read these as orders of magnitude.

3

A spinning disk has a read/write head on a moving arm. To reach a new place, the arm swings to the right track and waits for the spot to come round: a seek, about 10 ms. Then bytes stream past quickly, about 50 MB per second (2009 figures). Random I/O touches small pieces scattered around the disk: one seek per piece. Sequential I/O touches neighbouring bytes: one seek, then streaming. Reading 1 MB as 256 random 4 KB pieces costs about 256 × 10 ms ≈ 2.6 s; reading it in order about 20 ms, about 128 times faster (derived). Writes follow the same rule: updating records in place costs a seek each, while appending to a log is one stream. On SSDs the gap narrows but stays: about 38 ms against 1 ms per MB (derived, 2012 figures). In the 2006 Bigtable benchmark (1,000-byte values, paper Figure 6), one tablet server did about 8,850 random writes per second but only 1,212 random reads: writes had become log appends.

4

RAM forgets in a crash, and updating the disk in place is slow. A write is durable once it will survive a crash, and a database must not say "ok" before that point. The fix is a write-ahead log (WAL), or redo log. (1) Append a small record of the change, #104 "ben = 75", to the end of the log. (2) Call fsync and wait for the device to confirm; until then the bytes may still sit in an OS buffer. (3) Apply the change in memory. (4) Reply "ok". The data file still says ben = 20, which is fine: the log has the truth. Later a checkpoint writes the changes to the data file in one batch and moves the redo point, the log position up to which the data file is current. After a crash, the server loads the data file and replays the log from the redo point. Bigtable keeps its commit log in GFS, which by default stores three copies on different machines; a write counts as committed once its record is written there.

Forcing a log append to the device (a flush) has a fixed cost: waiting for the disk, or for the round trip to the machines holding copies of the log. If every write waits for its own flush, a server can never commit more writes per second than it can do flushes. Group commit removes that limit. While one flush runs, new writes queue up. When it finishes, all the queued writes go into the log as one append with one flush, and then all are acknowledged. In the picture, four writes finish in two flushes instead of four, and the last is done at 10 ms instead of 20. With toy numbers: if a flush takes 5 ms, one write per flush allows at most 200 commits a second; batches of 50 allow up to 10,000. Each write may wait up to about one extra flush, but none is acknowledged before it is durable. The 2006 paper says Bigtable uses group commit on its commit log to improve the throughput of lots of small mutations.

6

With writes made durable by the log, the question is how to organise the data files so lookups are fast. Two designs dominate, and they make opposite choices. A B-tree keeps entries sorted in fixed-size pages (a few kilobytes each) arranged as a short, wide tree. A lookup walks from the root to a leaf; the upper levels usually stay in memory, so it typically costs about one disk read. An update walks to the leaf, changes the entry and writes the page back to the same place: random I/O. B-trees are the classic choice of relational databases. A log-structured merge-tree (LSM-tree, O'Neil and others, 1996) never updates in place. A write is appended to the log and inserted into a sorted in-memory table, the memtable. A full memtable is written out whole, in key order, as a new sorted file (a flush), and background merges combine files. Disk writes are long and sequential; the price moves to reads, which may check several files.

A tiny LSM-tree after two flushes; keys are names, values are balances. File 1 holds ana 10, ben 20, cai 30, dev 40. Then ben became 25, ana 11, eli arrived, and "delete cai" was written as a tombstone: a marker saying "this key is deleted", because a file that never changes cannot have a value erased. That memtable became File 2. Now fay = 60 sits in the new memtable. Reads check newest to oldest and stop at the first answer. get ben: File 2 says 25; the older 20 is never read. get cai: File 2's tombstone answers "not found", so cai = 30 stays hidden. get dev: memtable no, File 2 no, File 1 yes, three places checked. That is the LSM read cost: every flush adds a file. In the background, a merge reads Files 1 and 2 in key order and writes File 3 with the newest version of each key. With no older file left, the tombstone and the cai = 30 it hid are dropped. Bigtable calls these steps compactions (deck 08).

8

Sorted files are quick to search. Take a 1 GB file with a million entries. Unsorted, you must read all of it: about 20 seconds at 50 MB per second. Sorted, you can binary search: check the middle, keep the half that can hold the key, repeat. A million entries need about 20 probes, but on disk each probe is a seek: 20 × 10 ms = 200 ms. Sorted with a block index: cut the file into blocks (typically 64 KB in the 2006 Bigtable) and store at the end a small index of each block's first key. Load the index into memory when the file is opened. Now the binary search runs in RAM, and the disk is touched once, for the one block that can hold the key. The index is tiny: a 128 MB file of 64 KB blocks has 2,048 blocks, about 200 KB of index even at 100 bytes per entry. Sorted order also makes range scans cheap: find the start once, then read forward. Deck 06 opens Bigtable's file format, the SSTable.

9

A file is immutable when, once written, it is never modified: it is created, read, and eventually deleted whole. LSM files are immutable, and that one property simplifies a lot. What it buys: a cached block can never go stale. Readers need no locks, because no writer will ever touch the file. A file is copied once and checked with a checksum. A crash halfway through writing a new file leaves the old ones untouched; the half-written one is thrown away. Two owners can share one file without coordinating. What it costs: updates and deletes do not free space at once, deletes need tombstones that every read must respect, background merges use disk bandwidth and CPU, and until a merge a read may check several files. The Bigtable paper credits immutability with three simplifications: reading SSTables needs no synchronisation (only the memtable is both read and written), deleting data becomes garbage-collecting whole files, and a splitting tablet shares its parent's files instead of copying them.

Two more tools complete a storage engine; deck 09 covers each in depth. Compression replaces repeats with short references to an earlier copy. Sorted order helps by putting similar rows side by side: Webtable's reversed-URL keys (com.cnn.www) keep a site's pages together, so shared boilerplate repeats close by. One 2006 experiment reports 10-to-1 for Webtable page contents, against the 3-to-1 or 4-to-1 Gzip typically gets on HTML. Compress each block on its own, so reading one entry decompresses only its block. The CPU cost is small: about 3 µs to compress 1 KB (2009 figures), against 10 ms for a seek. A cache keeps copies of recently used data in memory. It works because access is rarely uniform: the same item is asked for again soon, or its neighbours are. Bigtable's tablet servers have one cache for each: a Scan Cache of key/value pairs recently returned and a Block Cache of whole blocks read from storage. A read goes only as deep as the first layer that has the data.

11

The weak spot of an LSM-tree: a read for a missing key may have to check every file, each at the cost of a disk read. Such lookups are common: has this payment request been processed already? Has this URL been crawled? They do the most work and return the least. A Bloom filter is a small array of bits kept in memory for each file. It answers "could this file contain this key?" with "definitely not" or "maybe". It never says "definitely not" for a key that is there, so it cannot cause a wrong answer. For absent keys it wrongly says "maybe" only a small fraction of the time: about 10 bits per key gives roughly 1%, and each costs one wasted read. In the picture, all three files answer "no" from memory, so the duplicate check never touches disk. Files never change, so each filter is built once. In the 2006 paper Bloom filters were optional, chosen per locality group; deck 09 shows how the bits work.

Bigtable is an LSM-tree plus distribution. Each tablet, a range of rows (about 100 to 200 MB in 2006), is its own small LSM-tree: a memtable in the tablet server's RAM, SSTables in GFS, and its share of the server's commit log. In 2006 each tablet server looked after ten to a thousand tablets. Writes (amber) go to the commit log in GFS, then the memtable; a full memtable becomes a new SSTable (a minor compaction), and SSTables are merged over time (merging and major compactions). Reads (teal) see a merged view of the memtable and the SSTables, sped up by the block index, caches and Bloom filters. The red dashed box (server RAM) is lost in a crash; the green one (GFS) survives, so any server can pick up the tablet afterwards. The paper itself calls the design analogous to the LSM-tree. Cloud Bigtable, 2026: a 2023 Google Cloud blog post says it still stores data in a log-structured merge tree; the files now live in Colossus, GFS's successor.

NEXT Deck 04 · The data model

13

Five ideas to keep. First, the hardware: a RAM read takes about 100 ns and a disk seek about 10 ms (2009 figures), so engines keep hot data in memory and write to storage in long sequential runs instead of jumping around. Second, the write-ahead log: append the change, force it to the device, then apply it in memory and reply; after a crash, replay the log from the redo point. Group commit lets many writes share one flush, multiplying throughput without weakening durability. Third, an LSM-tree buffers writes in a sorted memtable, flushes them as immutable sorted files and merges in the background; reads check newest to oldest, and a tombstone counts as an answer. Fourth, a sorted file with an in-memory block index finds any key with one disk read, and files that never change make caching, concurrency and crash recovery simple. Fifth, Bigtable is one such LSM-tree per tablet, with its commit log and SSTables in GFS (today Colossus). Next deck: the data model those tablets hold.
