DECK 13 · Review

Where Bigtable sits among HBase, Cassandra and Spanner

When to pick Bigtable, and when to pick something else

One payment written, read and recovered, end to end

This is the last deck of the series, and it teaches nothing brand new. It does two jobs. First, it zooms out: one 2006 paper became the blueprint for a whole family of databases, and Google’s own next systems grew out of what Bigtable could not do. We draw that family tree, translate between the family’s vocabularies, compare Bigtable with Cassandra on how they spread and copy data, and end with a practical guide to choosing a Google Cloud database, including when Bigtable is the wrong tool. Second, it zooms in: one fictional payment is written, read back and survives the crash of the machine that holds it, so every part from the earlier decks appears in one story. As always, "2006" or "the paper" means the system the paper describes, and "Cloud Bigtable" means the service as documented in 2026.

The paper shipped no code, so others rebuilt it from the text. Read the tree left to right: copy, mix, extract, extend, rent. Copy: HBase began at Powerset at the end of 2006 and first shipped inside Hadoop 0.15 in October 2007; Hypertable (Zvents, 2007) was a C++ rebuild whose company closed in 2016; Accumulo came from the US National Security Agency in 2008 and added a security label on every cell. Mix: Facebook built Cassandra for Inbox Search in 2008 from Amazon’s Dynamo (2007) for distribution and Bigtable for the data model and storage engine. The dashed boxes are not descendants: Dynamo is Cassandra’s other parent, and Google’s own products never stopped running on Bigtable. Extract: in 2011 two Bigtable authors open-sourced LevelDB, a library "similar in spirit" to one tablet; Facebook forked it into RocksDB in 2012. Extend: Percolator (2010), Megastore (2011) and Spanner (2012) added what Bigtable lacked. Rent: Cloud Bigtable, beta in 2015 and GA in 2016.

Leaving HBase

Box and Flipkart moved from HBase to Cloud Bigtable. Coprocessors and snapshots stay behind.

3

Most confusion between these systems is vocabulary. HBase is the paper with new labels: a region is a tablet, a RegionServer is a tablet server, the HMaster is the master, ZooKeeper plays Chubby and HDFS plays GFS. Cassandra’s rows look different because it has no master, uses gossip between nodes for membership, and keeps files on each node’s own disks. The trap is in the last two rows. In the paper, a minor compaction turns the memtable into a new SSTable; HBase, Cassandra and RocksDB call that a flush. HBase then uses "minor compaction" for what the paper calls a merging compaction: a few files rewritten into one. Only "major compaction" means the same in Bigtable and HBase. Translate by what the step does, not by its name. The grid shows 2006 terms. In Cloud Bigtable, tablet servers are called nodes, Colossus replaces GFS, and frontend servers route requests. Moving from HBase is often mostly a client swap, but coprocessors, custom filters, namespaces, snapshots and per-cell access labels are unsupported.

A branch’s month-end statements

4

Same payments rows, two layouts. Bigtable sorts the whole table by one key and cuts it into ranges (tablets), so accounts 8800 to 8899 sit side by side on one server: a range query is one contiguous scan. Cassandra and DynamoDB hash first, then sort. The partition key (the account id) is hashed to choose a node, and rows are sorted only inside each partition, by a clustering column in Cassandra or a sort key in DynamoDB. One account’s history is still fast: one partition, already sorted. But a range of accounts is scattered by the hash, so the only way to find them is to ask every node. Each design has its own key rules. Keys that start with a timestamp are a hotspot in Bigtable because every new write lands in the last tablet; a hash spreads them. And Bigtable can split a huge entity across tablets at any row boundary, while a hash-partitioned system keeps a partition whole on its replicas, so unbounded partitions are a risk there.

A card block vs a like count

A block must show on the very next read; a like count can lag a moment.

5

One payment write for account 8812, through both designs. In Bigtable the client’s location cache names the one tablet server that owns the row’s range. The write goes to that server, which appends it to its commit log in GFS (three byte-for-byte copies) and replies. The master assigns owners but stays off the data path. In Cassandra any node can act as coordinator. It hashes 8812 to a point on the ring, and the next three nodes clockwise hold the copies (replication factor 3). It forwards the write to all three and replies once the consistency level is met: at QUORUM, 2 of 3. Each replica logs it on its own disk, Bigtable-style. Failure shows the trade. Bigtable’s rows on a dead server pause until the master reassigns them; nothing is lost and no copies disagree. Cassandra keeps accepting writes, but copies can disagree for a while, so it needs hints, repair and last-write-wins. A card block needs the very next read to see it; a like count can lag. Memory hook: Dynamo outside, Bigtable inside.

6

Bigtable makes every change to one row atomic, and nothing larger. Moving 100 from account A to account B touches two rows, so a crash between the two writes would create or destroy money. Google answered this gap three times. Percolator (2010) is a library on top of an unchanged Bigtable: each row gets a lock column and a write column, a timestamp oracle hands out times, and the whole transaction commits with one single-row write in a primary row. Google’s Caffeine indexing ran on it and cut the average age of documents in search results by 50%, at roughly twice the resources. Megastore (2011) keeps each entity group’s log in one root row and copies it across datacenters with Paxos; Gmail and Calendar used it, but its paper advises only a few writes per second per group. Spanner (2012) is a new system beside Bigtable: Paxos per shard, two-phase commit and TrueTime clocks; a write took about 14 ms in its paper’s tests. Ledger versus firehose: Spanner took the transaction jobs, Bigtable kept the huge key-and-range jobs.

Inside Google Cloud you usually choose between six managed databases, and the order of the questions matters: the first yes decides. Analytics, meaning big scans and totals over everything, goes to BigQuery, the data warehouse. If several rows must change together, or you need joins, go to Spanner, which has multi-row ACID transactions; if the app fits comfortably on one server, Cloud SQL (managed MySQL, PostgreSQL or SQL Server) is simpler and cheaper. App objects that need live sync or offline use belong in Firestore. A temporary copy that must answer in under a millisecond and can be lost goes in Memorystore (managed Valkey or Redis). Only then: terabytes or more, huge throughput, reads by one key or a key range? That is Bigtable: time series, events, IoT, transaction histories, personalization, ML features. The right-hand column is one fictional payments platform, with one job for each database. Treat the flow as a rule of thumb, not a substitute for testing your own workload.

8

Bigtable is the wrong tool in five situations. Several rows must change together (transfers, double-entry bookkeeping, inventory with orders): Bigtable guarantees only one row, so use Spanner or Cloud SQL. Questions are ad hoc, with filters on any field, joins or totals over everything: that is BigQuery’s job. The data is small: with less than several GB, all of a table’s tablets sit on one node and you still pay for provisioned nodes when idle. You may hear a rough 1 TB lower bound; the 2026 docs give no fixed minimum. Indexes must always match the table exactly: Bigtable’s continuous materialized views update asynchronously. Every region must read the latest write: Bigtable’s replication between clusters is eventual. Real systems mix databases. In Google’s published customer stories, Macy’s keeps prices by store and product in Bigtable and inventory and catalogue in Spanner; Ford Pro serves vehicle telemetry from Bigtable and runs long reports in BigQuery; YouTube writes upstream in Spanner and serves creator dashboards from Bigtable. Read them as case studies, not neutral benchmarks.

09:15 · a café payment of 42.50 EUR

9

One story, using the 2006 design. At 09:15 a customer of a fictional payments platform pays 42.50 EUR at a café from account 8812. The app builds one mutation: five cells in row acct#8812#…5807, so all five land or none. On a location-cache miss the client makes three round trips: the Chubby file names the server holding the root tablet (ts-04), the root tablet names the METADATA tablet (on ts-09), and METADATA says P is on ts-17. The master is never asked. The mutation goes straight to ts-17, which appends it to its single commit log in GFS in one group-commit batch. GFS stores that append on three servers: the commit point. Only then does the payment enter P’s memtable, and ts-17 replies (the paper only says the reply follows the log append). Later a minor compaction flushes the memtable to a new SSTable. With a warm cache only the send and the append remain. That is why, in the benchmark table in the paper’s Figure 6, random writes (8,850 per second) matched sequential ones (8,547).

09:20 · she scrolls her last 50 payments

Newest first is plain key order: one scan, and her older history is never read.

10

At 09:20 she opens the app. Row keys end in a reverse timestamp, so newest first is simply key order and the request is one range scan from acct#8812# to acct#8812$ (the $ is the byte after #), limited to 50 rows. The location cache says P is on ts-17: no lookups. The Scan Cache misses, so ts-17 opens one cursor per source: the memtable in RAM and each SSTable, whose block index is in memory. SSTable 3’s block is already in the Block Cache; SSTables 2 and 1 each cost one 64 KB read from GFS. The server merges the sorted streams. For each cell the newest version wins: yesterday’s 18:40 payment shows REVERSED from the memtable, hiding PENDING in SSTable 3. A server-side filter keeps only the txn family and the newest version, and after the 50th row the merge stops. Bloom filters do not help a range scan, which has no single row to ask about. In the 2006 benchmark table (paper, Figure 6) scans were the fastest operation: 15,385 values per second on one server.

11

At 09:31 ts-17 loses power. It owned tablets P, Q and R. Its memtables vanish, but nothing committed is lost: the commit log and every SSTable sit in GFS with three replicas. Six steps follow; the mnemonic is Even Good Drivers Avoid Sudden Reversing. E: with no KeepAlives, ts-17’s Chubby session expires and Chubby releases its lock. G: the master, already suspicious, grabs that lock, proving Chubby works and ts-17 cannot be serving. D: the master deletes ts-17’s file, so ts-17 can never serve again even if it returns (fencing). A: P goes to ts-22, Q and R to ts-31. S: ts-17’s log is cut into 64 MB segments that several servers sort in parallel, so each tablet’s records sit together. R: ts-22 reads P’s METADATA row, loads its SSTable indexes and replays only P’s records after the redo point. The app’s retry fails once at ts-17, re-reads METADATA and succeeds on ts-22: about two extra round trips. In Cloud Bigtable a node failure moves only metadata, and the docs say no data is lost.

12

Trace each guarantee back to its mechanism and the same three ideas keep appearing. One owner per tablet, enforced by a Chubby lock and fencing, gives single-row atomicity, no split brain, and reads that see acknowledged writes. Its price: when an owner dies, its rows pause until another server takes over. A write-ahead log in shared, replicated storage gives durability, fast writes (one group-commit append, no disk reads) and fast recovery, because any server can replay the log. Its price: after a crash the log tail must be replayed, which is why minor compactions keep it short. Immutable sorted files give reads without locks, splits that share files, compression and clean-up by garbage collection. Their price: background compactions, and deleted data that lingers until a compaction removes it (a major compaction in the paper; about a week in Cloud Bigtable). Two things were never promised: atomic changes across rows, and, in Cloud Bigtable, strongly consistent reads across clusters. In library terms: one librarian per volume, a daybook written in ink first, and printed booklets that are reprinted, never edited.

14

Five things to keep from this deck. One: Bigtable’s family has five branches. HBase copied it, Cassandra mixed it with Dynamo, LevelDB extracted one tablet, Percolator, Megastore and Spanner extended it, and Cloud Bigtable rents out the original. Two: Bigtable sorts one key space and gives each tablet one owner, so a failure means a short pause; Cassandra hashes keys onto equal replicas, so writes continue but it needs tunable consistency and repair. Three: pick Bigtable for huge, fast key-and-range workloads, Spanner for multi-row transactions, BigQuery for analytics, and remember the five signs that Bigtable is the wrong tool. Four: a write logs, then inserts, then replies; a read merges the memtable with the SSTables, newest first; a crash is handled by lock, fence, reassign and replay. Five: one owner, one log and sealed files carry almost every guarantee. This is the end of the series. To keep it, review on day 1, day 7 and day 30: redraw the whole system from memory, then retell this deck’s payment story out loud.
