The Data Model

A sorted map of maps, and why the row key you choose matters most

DECK 04 · The Bigtable model

How every value gets a four-part address

Why the row key decides where your data lives

How families, versions and one-row atomicity work

This deck takes apart the paper’s one-sentence definition of Bigtable: a “sparse, distributed, persistent multidimensional sorted map”. By the end you should be able to point at any value and say its full address (row key, column family, qualifier, timestamp), predict how row keys sort, explain what a column family controls, describe how versions are kept and garbage-collected, and model a real workload (a payments ledger) as a tall table. Throughout, we separate what the 2006 paper says from what Cloud Bigtable does as of 2026. The single most important lesson: the row key is the only index Bigtable gives you, so the key you choose decides which rows are neighbours, which queries are cheap, and how the load spreads across servers.

This is one row of the Webtable, the running example of the 2006 paper: a shared copy of the crawled web. The crawler re-downloads www.cnn.com every few days. The row key is the reversed hostname, com.cnn.www. The contents family holds the page itself in three versions (t3, t5, t6), newest first, so a read meets t6 first (teal). The anchor family has one column per site that links to CNN: the column name is the linking site, the value is the link text. Sports Illustrated (cnnsi.com) links with “CNN”; my.look.ca links with “CNN.com”. The language family records the page language (the “EN” value is illustrative). A relational database would need three or four tables (pages, page versions, links) plus joins; Bigtable puts it all in one row. A student’s school file works the same way: report cards by year are versions, and each teacher’s note is filed under that teacher’s name, like one anchor column per site.

3

Bigtable is a map: give it a key, get back a value. Its key has several parts. The paper writes the type as (row:string, column:string, time:int64) → string. The column key itself is two parts, family:qualifier, so the full address of one value has four parts: row key, family, qualifier and timestamp. The nested boxes show the “map of maps” you can carry in your head: the row picks one entry, the family picks a section of it, the qualifier picks one column, and the timestamp picks one version. Each level holds sorted keys, and the grey boxes are the siblings you did not open. The value is an uninterpreted array of bytes. Bigtable never parses it, so it cannot check, index or sort values as numbers; your application chooses the encoding. (Cloud Bigtable adds a few typed exceptions, such as increments that treat a cell as an 8-byte integer and aggregate families.) Like the office archive, you name the place precisely and get back exactly one thing, unread.

4

Bigtable keeps rows in lexicographic order of their row keys, compared byte by byte from the left, the way a dictionary orders words. Because the table is sorted, it can be cut into contiguous row ranges called tablets, and each tablet is served by one tablet server at a time. In the 2006 paper a tablet is about 100–200 MB by default and one server looks after roughly ten to a thousand tablets. A new table starts as one tablet and splits as it grows. The payoff is locality: rows whose keys start the same way are neighbours, so they usually land in the same tablet. The teal range scan for every key starting com.google. reads one contiguous block and talks to one server, instead of thousands of scattered lookups. The same property explains the price: your choice of key decides which rows are neighbours, so it controls locality, load and even compression. Like encyclopedia volumes, each covering one range of headwords, you only take down the volume you need.

5

Lexicographic order compares keys one byte at a time from the left. The first byte that differs decides; if one key runs out first (it is a prefix of the other), the shorter key comes first. So row1 comes before row10, which comes before row100, and all of them come before row2 and row9. At the fourth byte of row10 and row9, the character 1 (byte 0x31) is smaller than 9 (0x39), so row10 wins. The fix is to pad numbers to a fixed width: row001, row002, row009, row010, row100. Then byte order and numeric order agree. Two more surprises from the byte ladder: every uppercase ASCII letter (0x41–0x5A) sorts before every lowercase one (0x61–0x7A), so Zebra comes before apple; and punctuation such as # (0x23), - (0x2D), . (0x2E) and / (0x2F) sorts before all digits and letters, so the separator you choose affects where keys land. The folder-of-files example is the same trap you have probably seen on your own computer.

Because rows are sorted and sorted ranges become tablets, the key decides which rows end up together on disk and on the same server. The Webtable’s trick is to reverse the hostname: the page maps.google.com/index.html is stored under the key com.google.maps/index.html. Sorted as written, the three google.com pages are scattered across the table (left). Reversed, the key starts with the most general part (com, then google), so all of google.com sits in one contiguous block of rows (right): one range, most likely one tablet. A job that analyses one domain reads one range, and pages from the same site share boilerplate HTML, which compresses better when stored side by side. Cloud Bigtable’s schema guide still recommends reversed domain names, with a warning: the trick works when data is spread over many domains. With only a few domains it risks hotspots and rows that grow too large. Deck 12 covers key design rules in depth.

7

A column key has two parts, family:qualifier, and they behave very differently. Families are declared, few and stable: a family must be created by an administrative operation before anything is written under it. The paper wanted only a few families per table (hundreds at most); Cloud Bigtable recommends about 100 at most. The schema is drawn violet because it is control-plane data: in the paper the master handles family creation and Chubby stores each table’s family list. Qualifiers are free: once a family exists, writing anchor:news.example.org creates that column on the spot, with no ALTER TABLE, and each row has its own set. A family is the unit for settings: in the 2006 paper, access control, disk and memory accounting, compression and garbage collection; in Cloud Bigtable, mainly the garbage-collection rule (access is granted on projects, instances, tables and views, and compression is automatic). The Webtable keeps the newest 3 versions of every page. A contact card works the same way: fixed sections, labels you add as needed.

8

Picture the Webtable as a spreadsheet: one row per page (p1–p5) and one column per linking site (s1–s6). In the real Webtable there are millions of linking sites, so almost every cell is empty: a typical page is linked from a handful of sites, not all of them. A relational table must give every row a slot for every column, holding NULL if empty. Bigtable stores only the cells that have values: here 7 entries instead of 30 slots. An absent cell takes no space and needs no NULL marker. That is what sparse means. A real case from the paper: Google Earth’s imagery preprocessing table has a family with essentially one column per raw image, and each geographic segment uses only a few images. The flip side: every stored cell carries its own coordinates (row key, column name, timestamp). Cloud Bigtable’s documentation recommends short qualifiers and notes that storing 1 KB in one cell is more efficient than 1,024 cells of one byte each. Empty is free; many tiny filled cells are not.

Each cell can hold several versions of its value, each tagged with a timestamp. Timestamps are 64-bit integers. If Bigtable assigns one, it is the real time in microseconds; clients may also set their own, with any meaning they like (the Webtable uses the crawl time). Versions are stored in decreasing timestamp order, so a read meets the most recent one first (teal). Panel 1: the first crawl writes t3. Panel 2: re-crawls at t5 and t6 go on top. Panel 3: a delayed crawler writes a version stamped t4. It is placed by its timestamp, below t5, not on top: order follows the timestamp, not arrival. If two writes must never collide, the client has to make timestamps unique. Cloud Bigtable keeps 64-bit microsecond values but with millisecond precision (the number must be divisible by 1,000), so two writes in the same millisecond can collide. Like a Wikipedia page history, the newest edit is on top and older ones stay available.

10

Old versions are garbage-collected per column family: Bigtable deletes versions automatically according to a rule you set. The paper offers two settings: keep only the last N versions of each cell, or keep only versions that are new enough (for example, written in the last seven days). The Webtable keeps the three most recent versions of every page. Cloud Bigtable adds combinations: a union (delete if any rule matches) and an intersection (delete only if all match), nested if needed. Eligible does not mean gone. Old versions are physically dropped later, when a compaction rewrites the tablet’s files. The paper does not say exactly when; Cloud Bigtable says it can take up to about a week, and until then the version can still appear in reads. If your code must never see it, add a read filter that mirrors the rule. Defaults differ by tool: the console, gcloud, cbt and most client libraries keep unlimited versions; the HBase client keeps one. Set a rule on purpose. Phone backups behave the same way: old ones are cleared in the background.

IN THE REAL WORLD

A bank clerk’s account cards. One card: one edit, done or not. Moving money between two cards: two edits; stop halfway and only one changes.

11

Every read or write under a single row key is atomic (all or nothing), no matter how many columns it touches. If the crawler writes a new contents: version and a new language: value in one mutation, no reader can see the new page with the old language: it sees both changes or neither. The paper’s reason is simple: it makes concurrent updates to the same row easy to reason about. The guarantee stops at the row boundary. A change that touches two rows is two separate atomic writes, and a crash between them leaves one done and the other not. In the payments example, writing a payment row and updating a separate balance row is not atomic. Designs either avoid needing that (for example, by deriving balances from the payment rows) or use a database with multi-row transactions for that step. Even a batch of writes to several rows sent together can partly succeed (deck 05). The guarantee comes from one server owning a row at any moment (deck 07).

THE REVERSE TIMESTAMP

reverse = (2^63 − 1) − time in ms

Later payments get smaller numbers, so they sort first. Keep all 19 digits.

12

A fictional global payments platform stores every transaction for every account. The query that matters most is “show the last 50 transactions for account 8812, newest first”, and writes arrive at high volume across millions of accounts. Wide design: one row per account, one column per payment. The row grows without limit; Cloud Bigtable recommends keeping a row under 100 MB and has a hard limit of 256 MB. Tablet boundaries fall between rows, never inside one, so a giant row can never be spread over servers. Tall design: one row per payment, keyed acct#8812#<reverse timestamp>. Rows stay small, the account’s rows share a prefix so they are contiguous, and “the last 50” is the first 50 rows of the prefix. Reverse timestamp = (2^63 − 1) − time in ms, so a later time gives a smaller number that sorts first: 09:15:00 UTC on 3 October 2026 gives 9223370245835875807; one second later gives …874807. Keep it a fixed 19 digits; append a transaction ID if two payments can share a millisecond.

13

The model has barely changed since 2006, but the limits have. Row keys: up to 64 KB in the 2006 paper (10–100 bytes typical), and a hard limit of 4 KB in Cloud Bigtable as of 2026. Keep them far shorter than either, because the key travels with every cell. Families: “hundreds at most” in the paper; about 100 per table recommended today. A single row: Cloud Bigtable recommends under 100 MB and has a hard limit of 256 MB (the paper gives no figure). Qualifiers: keep each under 16 KB. Timestamps: 64-bit microseconds in both, but Cloud requires millisecond precision. Old versions: removed at compaction in both; Cloud says this can lag up to about a week. Check the Cloud quotas page for current limits. The pitfall: versions are not a free time-series database. Storing a sensor’s readings as millions of versions of one cell makes one row grow without bound. Cloud Bigtable’s time-series guidance uses new rows, or bounded time-bucket rows (one per sensor per hour) with a GC rule.

14

Five ideas to keep. First, every value has a full address: row key, family, qualifier and timestamp, and the value is raw bytes. Second, rows are sorted as bytes and the row key is the only index, so design keys so each important query is a contiguous range: pad numbers, reverse hostnames, put the field you query by first. Third, families are schema (few, declared, carrying settings such as the GC rule); qualifiers are data (unlimited, created by writing); empty cells cost nothing, but filled cells carry their names. Fourth, versions are ordered by timestamp, newest first, and a per-family rule keeps the last N or the recent ones, with physical removal later, at compaction. Fifth, atomicity covers exactly one row, so data that must change together belongs in one row, and event data starts as a tall table keyed like acct#8812#<reverse timestamp>.
