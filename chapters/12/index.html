Schema Design and Real Workloads

Row keys, hotspots and column families, worked through sensors, payments and an inbox

DECK 12 · Bigtable today

Turn a ranked list of questions into a row key

This deck turns the Bigtable data model into design decisions. In Bigtable the row key is the index, the sort order and the load balancer at once: it decides which questions are cheap, which node does the work, and how big a row can grow. We start from the questions an application asks and derive a key from them. Then we see why some keys send every write to one node (a hotspot), why automatic splitting cannot rescue them, and what the four standard fixes cost. After that come reverse timestamps, the three shapes for time-series rows, column families with garbage-collection (GC) rules, and how to read the Key Visualizer heatmap. Three worked examples (two million sensors, a payments ledger and an activity inbox) apply the same recipe end to end. Numbers are Cloud Bigtable values as of 2026 unless marked as the 2006 paper; check the docs for current limits. All example data is fictional.

2

Bigtable keeps one map sorted by row key and cuts it into tablets: contiguous key ranges, each served by one node. That gives exactly three cheap ways in. An exact key fetches one row. A key prefix, such as acct#8812#, returns rows that sit next to each other, usually in one tablet. A key range, from a start key to an end key, returns a slice such as one month of an account's payments. Anything else is a full table scan: Bigtable reads every row and a server-side filter throws most of them away. Filters save network bandwidth, not the reading. (The teal slices are drawn wider than to scale.) So design runs backwards from SQL habits. Google's schema guide describes four steps: gather and rank the queries; design keys and families so the top queries become exact, prefix or range reads; test with at least 30 GB of realistic data under heavy load; then refine. A relational database lets you add indexes later. In Bigtable the key is the index.

A good key reads "who, then when, then which". The front field is what every important query already knows, here the account, so the account screen becomes a prefix scan, and millions of accounts spread the writes. Next comes the time, reversed so the newest payment sorts first: 2^63 − 1 minus the time in milliseconds, kept at 19 digits. Last comes a unique tail, the payment ID: two payments in the same millisecond stay distinct, and a retried write lands on the same row instead of creating a duplicate. Google used this shape in 2006: the paper's Google Analytics click table keyed each session by website name, then start time. The SPREAD mnemonic sums up the rules. Short: tens of bytes; Cloud Bigtable's hard limit is 4 KB (the 2006 paper allowed 64 KB, with 10 to 100 bytes typical). Prefix: what the top queries know. Readable: you will read keys in Key Visualizer. Even writes: never a time or counter first. Aligned: zero-padded, fixed width. Delimited: a scan for acct#88 also returns account 8812, so scan acct#88#.

WATCH OUT

More nodes won’t help

4

A hotspot is a small part of the key space that receives a disproportionate share of the traffic, so the node serving it is overloaded while others sit idle. Google defines a hot tablet as one using a disproportionately large share of its node's CPU. The classic cause is a monotonically increasing key: a timestamp or a counter-issued ID at the front. Every new key is larger than all stored keys, so it sorts into the last tablet, and one node takes 100% of the writes however many nodes exist. Put the entity first (car0412#time) and each car appends at the end of its own range, so new rows land in every tablet and each of the 8 nodes takes about an eighth. The same trap appears with a constant prefix followed by time, such as BATTERY#<time>. Google's 2022 hotspot article describes a cluster averaging about 60% CPU, under the recommended 70% ceiling, with its hottest node near 100%: that gap is the telltale sign. Extra nodes do not help a schema that sends traffic to a few rows.

5

Cloud Bigtable does split tablets to relieve load and moves the pieces to other nodes. Only pointers move, because the data stays in Colossus. That works when heat is spread over many rows in a range. With a timestamp-first key it does not. After a split at 09:10, every new key is later than 09:10, so all writes go to the newer half, now on node A, and the older half goes idle. Splitting also fails for a single hot row (a tablet holds whole rows, so no split can divide one row), for short bursts (rebalancing takes time; after adding nodes it can take up to 20 minutes under load), and extra nodes cannot share load that the key concentrates. The library analogy: file cards by arrival time and only the librarian with the last volume works; file by author and new cards scatter. In the 2006 paper, tablets were about 100 to 200 MB, a tablet server split one that grew too large, and the master moved tablets; the logic is the same.

A hot merchant Salt only the one account taking thousands of payments a second: acct#M77#3#….

6

Google's guidance ranks the fixes roughly in this order. Field promotion moves a field from the cell data into the key, in front of the time: BATTERY#Corrie#2015…. It avoids hotspots in almost all cases and often makes the main query a prefix scan, but the field needs many values and fairly even traffic: three values give three hot ends. Reversing a fixed-width counter ID (0001234567 becomes 7654321000) puts the fastest-changing digit first; you lose ID ranges, which rarely matter. Salting inserts a bucket number from a stable hash, such as crc32 mod N (never Python's built-in hash()). The picture uses N = 3, like Google's example. Writes spread into N streams, but every range read becomes N scans your code merges. Hashing the whole key spreads load evenly but destroys order and readable heatmaps; use it only for data read by exact key. With every fix, a point read is still one request, because the application can compute the full key. The hot merchant: 3 is crc32 of the transaction ID mod 8, so "latest 50" becomes eight merged scans.

WATCH OUT

7

Rows are stored in ascending key order. With a forward timestamp, the newest payments sit at the end of an account's range, so a forward scan meets the oldest first. Storing 2^63 − 1 minus the timestamp flips that: larger times give smaller numbers, so the newest row sorts first and "latest 50" means "read the first 50 rows of the prefix". Worked number: 09:15:00 UTC on 3 October 2026 is 1,791,018,900,000 ms, so its reverse value is 9223370245835875807; one second later the value is 1,000 smaller and sorts before it. Keep the field 19 digits wide, end the key with a unique tail such as the payment ID, and put the reversed time after the entity: at the front it is still monotonic and piles writes onto the other end. Other time ranges get awkward (the later instant gives the start key), so Google suggests this only when "latest" is the main query. The 2006 paper had forward scans only; Cloud Bigtable added reverse scans (GA end of 2023) for short reads of about 50 rows.

The same four readings from sensor 42 can be laid out three ways, and each keeps the sensor first and the time last. Tall and narrow, one row per event, was the default advice in Google's 2020 time-series guide: easy to query and rows never grow without limit, but many small rows read and compress less efficiently. Time buckets get more weight in the current docs: Bigtable writes and reads 100 measurements faster as one row than as 100 rows, and they compress better. Here the bucket is an hour, columns m:00 to m:59, then a new row. Size buckets so rows stay well under the recommended 100 MB (256 MB is the hard limit). Versions suit values that are genuinely amended, like Google's closing price corrected from 559.40 to 558.40, or a payment status moving from PENDING to SETTLED; prefer rows to versions for streams of events. Both guide editions agree: never let a row grow without bound, never put the timestamp first. In the watch example, a day's chart reads 24 rows instead of 1,440.

9

A column family is a named group of columns that share storage and garbage-collection settings. Families must exist before you write to them; qualifiers are created freely by writes. Design rules: few families (Cloud Bigtable recommends no more than about 100 per table; the 2006 paper hoped for hundreds at most), short names because names travel with every cell, columns read together in one family, and separate families for separate retention, because GC rules are set per family, never per column. In the payments table, txn holds amount, currency, counterparty and status, keeping 5 versions for the status history; risk holds the fraud score and flags, written by a different pipeline and kept 90 days. Two surprises catch almost everyone. Tables created with the console, gcloud, cbt or most client libraries keep unlimited versions unless you set a rule (the HBase client defaults to one). And GC runs during compaction, which in Cloud Bigtable can take up to a week; until then, expired cells still appear in reads, so add a read filter matching the rule when that matters.

A shop’s footfall heatmap Even traffic across the aisles is healthy; one aisle glowing all day is a bottleneck.

10

Key Visualizer is Cloud Bigtable's built-in heatmap of a table's traffic (these maps are sketches, not screenshots). Time runs left to right; row keys run top to bottom in sorted order, grouped into 1,000 buckets of roughly equal row counts. Stronger colour means more activity relative to the rest of the view, so a bright cell is not automatically a problem. Scan data is produced every 15 minutes and kept for 14 days, for tables with at least 1 GB per cluster. Even speckle is healthy. A bright diagonal means sequential keys, a time or counter first; it can also be a planned full scan, so ask whether it is reads or writes and whether you expected it. A horizontal hot band is one key range hot all the time: a big tenant, a celebrity account or a shared default ID. Repeating vertical stripes are load that arrives on a schedule across many keys. Because Key Visualizer aggregates over 15 minutes, short bursts can vanish into the average; gcloud bigtable hot-tablets list shows the hottest tablets at one-minute resolution.

Scenario (fictional): a cold-chain company fits two million sensors, each reporting temperature, humidity and battery once a minute: about 33,300 writes per second and 2.88 billion readings a day. Ranked questions: store each reading; chart one device over time; show the current reading of every device at a site; forget raw readings after 90 days; run a nightly fleet-wide analysis. Two tables, each keyed for one question. readings is keyed <device>#<yyyyMMdd>T<HHmm> in UTC, family m with a 90-day max-age rule: a day's chart is one range of 1,440 rows. latest is keyed <site>#<device> with one version: the dashboard is a prefix scan of site017#. Each reading is written twice; if the second write fails, the dashboard is a minute stale, which is acceptable here. The nightly job is a full scan, best run on Data Boost. Sizing, assuming about 100 bytes per reading on disk: roughly 26 TB for 90 days, or about 11 SSD nodes at autoscaling's default 2.5 TB per node. Storage, not traffic, sizes this cluster. Never put the date first.

12

Scenario (fictional): a payments platform with millions of accounts. No single key serves every question, so the design uses row types: kinds of rows told apart by a short prefix in one table, each with its own family and GC rule. Ledger entries acct#<acct>#<reverse ts>#<txnId> answer "latest 50" (a prefix scan with a limit) and the monthly statement (a range scan, where the later instant gives the start key). Request rows req#<id> make retries safe. Lookup rows txid#<txnId> hold the ledger key, so support finds a payment with two point reads. Velocity counters live in their own table, one row per account per hour, updated with AddToCell on an aggregate Sum family; the last 24 hours are 24 neighbouring rows. With no multi-row transactions, the service first claims the request row with check-and-mutate (write STARTED only if the row is empty), uses explicit timestamps so every step can be repeated, then marks it DONE. A resent request finds the claim and gets the stored result. Counter additions cannot be safely repeated, so the ledger is the record of truth.

Scenario (fictional): a photo-sharing app's activity inbox. The key is u#<userId>#<reverse ts>#<itemId>: the user gathers the rows, the reverse timestamp puts the newest first, and the item ID breaks ties. One family, ev, with a 90-day max-age rule, holds a denormalised copy of what the screen needs, so a page renders from one scan. Page 1 is a prefix scan from u#42# to u#42$ ($ is the byte after #) with a limit: 3 in the picture, 20 in the app. The app remembers the last key it showed, the cursor, and page 2 starts strictly after it. A new item at 10:12 sorts above page 1, so nothing on page 2 shifts: no duplicates and no gaps. An offset ("skip 40, take 20") would be slow, because the read API has a row limit but no offset, and wrong, because new items push old rows onto the next page. The end key stops the scan before user 43's rows. A very busy recipient makes its prefix a hot range: summarise, or salt that one account.

NEXT Deck 13 · Bigtable in the big picture

14

Five ideas carry this deck. The row key is the only built-in index, so design it from a ranked list of questions. Order key fields who, then when, then which: never time or a counter first, and reverse the time (after the entity) when newest-first is the main query. Splitting and extra nodes cannot fix a moving end or a single hot row; field promotion is the default fix, with reversed IDs, salting and whole-key hashing as narrower tools that each cost something on reads. Families follow reading and retention, each with a GC rule, remembering that GC happens at compaction, in Cloud Bigtable up to about a week later. Before going live, test with at least 30 GB of realistic data and read Key Visualizer: speckle is healthy, a diagonal or a band is a hotspot.
