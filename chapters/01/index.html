What Bigtable Is

What problem it solves, what it is, and how its parts fit together

DECK 01 · Start here

Why Google needed a new kind of storage system

What a sparse, distributed, sorted map is

Welcome to the first deck of "Bigtable, Visually". This deck is the map for the whole series. It answers three questions. What problem was Bigtable built to solve? What is it, in one sentence? And what are its main parts and how do they fit together? Bigtable is a storage system Google started building around early 2004, ran in production from April 2005, and described in a paper at the OSDI conference in November 2006, where it won a Best Paper award. Since 2015 anyone can rent it as Cloud Bigtable. Throughout the series we keep two eras apart: "2006 paper" means the internal system the paper describes, and "Cloud Bigtable" means the managed service as Google documents it in 2026. Every slide has one picture and one real-world example. The full explanation is in these notes, so you can study the deck on your own.

Around 2004 Google needed one place for copies of the web, years of clicks, search histories and satellite photos. The chart shows real production tables from the 2006 paper (Table 2), measured before compression. The web crawl table was about 800 TB; Google Analytics' raw click table about 200 TB; Google Earth's raw imagery about 70 TB. For scale: a typical 2009 server had about 2 TB of disk, so the crawl table alone would fill the disks of roughly 400 servers, before keeping any extra copies. (That 400 is our arithmetic: 800 TB divided by 2 TB.) And these tables were used in two opposite ways. Batch jobs read or rewrote whole tables and cared about throughput; serving requests had a person waiting and cared about latency in milliseconds. One system had to do both. By August 2006 more than sixty Google products and projects stored their data in Bigtable. Real-world example: Google Analytics records every page view on every website that runs its tracking script. That stream became a 200 TB table, far too big for one machine.

IN THE REAL WORLD

One giant truck, or a fleet of vans. The biggest truck has a size limit, and one breakdown stops every delivery. A fleet grows van by van, and when one breaks down the others take its parcels.

3

There are two ways to get more capacity. Scaling up (vertical scaling) means replacing a server with a bigger one. It needs no software changes, but it hits three walls: big machines cost more per unit of work, there is a largest model on sale, and it is still one machine, so when it fails everything on it stops. Scaling out (horizontal scaling) means adding more ordinary, mass-produced machines and spreading data and work across them. Google took this road: Bigtable and GFS, the Google File System, both run on commodity servers. The price is that something is always broken. Jeff Dean's 2009 figures for the first year of a typical new Google cluster include about 1,000 individual machine failures, about 20 whole-rack failures and thousands of disk failures. So Bigtable assumes failure: no server holds the only copy of anything, and a dead server's work moves to others automatically. Real-world example: a delivery company with one giant truck stops completely when it breaks down; a fleet of vans grows one van at a time and shrugs off one breakdown.

The 2006 paper defines Bigtable in one sentence: a sparse, distributed, persistent multidimensional sorted map. Read it backwards, from the noun. 1 Map: give it a key, get back a value, like a Python dict; the value is raw bytes that Bigtable never looks inside. 2 Sorted: rows are kept in row-key order, compared byte by byte, so similar keys sit together. 3 Multidimensional: each value has three keys: row, column and timestamp. 4 Persistent: the commit log and sorted data files live in GFS, which keeps three copies by default, so data outlives any machine. 5 Distributed: the sorted table is cut into tablets (row ranges), each served by one server at a time. 6 Sparse: only cells that hold a value are stored. Real-world example: a phone book. A name gives a number (map); names run A to Z (sorted); a person has home and mobile numbers in each year's edition (multidimensional); many copies are printed (persistent); a big city needs several volumes (distributed); nobody prints a blank line for a missing mobile (sparse). Deck 04 goes deeper.

You find any value in Bigtable with three coordinates: a row key, a column and a timestamp. The paper writes the type as (row:string, column:string, time:int64) → string, where the result is raw bytes. The grid is the paper's Webtable example: one row per web page, keyed by the reversed host name. The highlighted cell is row com.cnn.www, column contents:, and it holds three versions of the page, fetched at times t3, t5 and t6. Versions are stored newest first, so t6 is met first. A column name has two parts, family:qualifier. The family (anchor, contents, language) is declared in the schema; the qualifier is any string. In anchor:cnnsi.com, the qualifier is the site that links to CNN and the value "CNN" is the link text. Dashed cells are empty and are simply not stored: that is the "sparse" in the definition. Real-world example: a shared spreadsheet picks a cell by row and column, and its version history picks an older value. Bigtable puts the time inside the address itself.

6

Bigtable keeps rows sorted by row key and cuts the sorted table into tablets, each served by one server. So the key you choose decides which rows are neighbours, and which server holds them. This is the single idea that runs through the whole series. Picture a payments platform. On the left (A) each transaction is keyed by its transaction ID. Account 8812's transactions (highlighted) end up scattered across every tablet and every server. Bigtable indexes only the row key, so finding them means scanning the whole table. On the right (B) the key starts with the account and ends with a reverse timestamp: a large constant minus the transaction time, so newer transactions sort first. Now account 8812's rows sit side by side, newest first, and "the last 50" is one short scan (teal), usually on one server. Real-world example: a phone app asks for the last 50 transactions of an account and expects an answer in milliseconds. Decks 04 and 12 show how to design keys like this, and how to avoid hotspots.

7

The whole 2006 system on one page. Your application links a client library. Many tablet servers do the reading and writing; each serves roughly 10 to 1,000 tablets (2006 figures). One master assigns tablets to tablet servers, notices servers joining and dying, and balances load. Chubby is a small lock service with five replicas; it holds the master lock, a lock file per live tablet server, and the file that says where the root tablet is. The client finds the right server itself (via Chubby, the root tablet and the METADATA table, cached after the first time), then reads and writes directly with that tablet server. Client data never passes through the master, so it stays lightly loaded. Every file lives in GFS: the commit log and the sorted, immutable SSTable files, three copies of each chunk by default. Real-world example: when a server dies, other servers take over its tablets and replay its log. Cloud Bigtable today: tablet servers are called nodes, frontends route requests, and files live in Colossus. Decks 06 to 08 zoom in.

The whole series uses one analogy: Bigtable as a vast library whose entries are kept in strict alphabetical order. The table is the whole collection, one giant encyclopedia. The row key is the headword on each entry. A tablet is one volume, such as "Aa to Am". A tablet server is a librarian who looks after a shelf of volumes and serves readers directly. The master is the head librarian: decides which librarian keeps which volume and never fetches books for readers. Chubby is the front-desk registry with a notary's stamp: who works here today, who is head librarian, where the master catalogue is. The commit log is the daybook, where every change is written first, in ink. GFS is the warehouse that stores every booklet and daybook, with copies in several buildings. Where the analogy breaks: librarians own nothing. Because the files live in the warehouse, a volume moves to another librarian without carrying any books; the paper reports a moved tablet is typically unavailable for under a second.

9

To run on thousands of cheap machines, the 2006 Bigtable left out most relational features. No joins: your code or a MapReduce job combines tables. No multi-row transactions: a write to one row is atomic, but nothing spanning two rows is. No SQL: the 2006 interface is a library of calls. No secondary indexes: only the row key is indexed. No typed columns: values are raw bytes. Why acceptable? Google's data had natural keys (a URL, a user ID), heavy cross-data work ran as batch jobs, and most apps needed only single-row transactions. In return it grows by adding machines, survives failures, reads fast by key and key range, and lets you choose locality and memory or disk. Then vs now: Cloud Bigtable added GoogleSQL (generally available April 2025) and continuous materialized views (April 2026); one row is still the atomic unit. Real-world example: a shopkeeper finds anything you describe, like SQL; a warehouse picks only by bin number, yet ships millions of orders. Watch out: moving $50 between two accounts is two row writes; one can fail alone.

By August 2006 more than sixty Google products and projects used Bigtable, including web indexing (crawl tables up to about 800 TB), Google Analytics (every page view on every tracked site), Google Earth (satellite imagery, prepared by batch jobs and served from a fast index), Personalized Search (each opted-in user's queries and clicks), Orkut, Google Finance and Writely, which became Google Docs. There were 388 non-test clusters with about 24,500 tablet servers. Since 2015 anyone can rent it as Cloud Bigtable; the beta was announced as the database behind Google Search, Gmail and Analytics. Google's published customer stories include Macy's (prices by store and product), Ford Pro (real-time vehicle telemetry), YouTube (creator dashboards) and migrations from HBase (Box, Flipkart) and from Cassandra (Spotify's monitoring system, Palo Alto Networks). These are case studies from Google's own blog, not neutral benchmarks. Google has reported more than 10 exabytes stored (2022 to 2025) and a peak of 7 billion requests per second (April 2024; the post does not say whether that is all of Bigtable or Cloud only).

11

Bigtable did not stop in 2006. Design began around early 2004 (sources differ between late 2003 and early 2004). It ran in production from April 2005, after roughly seven person-years of work, and the paper appeared at OSDI in November 2006, winning a Best Paper award. The paper inspired a family of systems (hollow dots). HBase, an open-source copy, first shipped inside Hadoop 0.15 in October 2007. Facebook open-sourced Cassandra in 2008: Amazon Dynamo's way of distributing data plus Bigtable's data model. In 2012 Spanner became Google's database for cross-row transactions. Bigtable itself (filled dots) became a public service: Cloud Bigtable beta in May 2015, generally available in 2016. Autoscaling and clusters in up to 8 regions arrived in December 2021, GoogleSQL became generally available in April 2025, and continuous materialized views in April 2026. Through all of it the engine stayed the same: sorted rows, tablets, a log plus sorted files on a shared file system, single-row atomicity. Real-world example: the same payments write, twenty years apart. Deck 11 covers Cloud Bigtable in detail.

What to remember

A sparse, distributed, persistent, multidimensional sorted map: (row, column, time) → bytes.

TEST YOURSELF

Q1. Do reads go via the master?

Answer: No. They go straight to the tablet server.

Q2. A tablet server dies. Is data lost?

Answer: No. Its log and files live in GFS.

Q3. Can one write move $50 between two rows?

Answer: No: atomicity is per row.

13

Four ideas to keep from this deck. First, the definition: a sparse, distributed, persistent, multidimensional sorted map, where a row key, a column and a timestamp find a value of raw bytes. Second, Bigtable scales out: rows are sorted by key, the table is cut into tablets, and each tablet is served by one tablet server at a time. Because rows are sorted, the row key you design decides which rows sit together, and so how fast you can read them. Third, control on the side, data straight through: the master and Chubby decide who serves what, clients read and write directly with tablet servers, and every file lives in GFS (Colossus today). Fourth, the bargain: no joins, no SQL in 2006, no multi-row transactions and no secondary indexes, in return for a system that grows by adding machines and keeps serving when they fail. Answer the three questions out loud before reading the answers. Then move on to Deck 02, which explains the distributed-systems ideas Bigtable relies on.
